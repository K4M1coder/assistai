# EXP-202: Haru-4B as a French full-duplex candidate

## Hypothesis

An explicitly multilingual native full-duplex model could meet the French barge-in requirement more directly than the current English-only-supported LFM3-Audio conversation path. Haru is a candidate, not a demonstrated solution.

## Evidence

[Haru-4B's model card](https://huggingface.co/higurashi-ai/Haru-4B) describes a continuous full-duplex research model supporting French and eight other languages, with 133 ms audio frames and simultaneous audio input, text and audio output. It also explicitly says the pretrained base is not a reliable factual or instruction-following assistant. Its card lists Apache 2.0 weights; review third-party notices before distribution. The author documents approximately 12 GB GPU memory for an NVIDIA example, not an Intel B60 measurement. The published [model files](https://huggingface.co/higurashi-ai/Haru-4B/tree/main) include an approximately 10.5 GB BF16 safetensors checkpoint; disk size is not total GPU consumption. The model repository resolved to revision `8d6e83bcd3701a76fc27a764965665da1df7da78` on this review.

The [implementation](https://github.com/higurashi-ai/Haru/tree/7fe6b7665f8bf035998f401f8cb779fbe53f2751) was inspected at commit `7fe6b7665f8bf035998f401f8cb779fbe53f2751` without executing it or downloading weights. Its PyTorch loader defaults to CUDA when available and otherwise CPU, accepts an explicit device, and loads the BF16 safetensors checkpoint; explicit device support is not proof that all operators or the loader work with Intel XPU. Its optional fast codec uses CUDA/Triton; the repository also describes plain implementations. The reviewed model card and README do not document structured tool calls. Treat that as an unverified capability, not proof that none could be engineered. The repository identifies third-party components and the voice-reference requirement.

## Budget and decision

The most recent running-demo sample was about 11.3 GB dedicated GPU usage. Adding the publisher's approximately 12 GB NVIDIA figure would leave little apparent room under a nominal 24 GB limit before accounting for differing hardware, contexts, concurrency and transient allocations. These numbers are neither additive measurements nor a guarantee; the 22 GiB experimental reserve threshold may also reject such a configuration. No validated quantized Haru or quantized KV implementation for this runtime and B60 was established. Do not load this checkpoint alongside the current services on that estimate.

Haru merits an isolated research comparison because its claimed French full-duplex behavior addresses a central requirement. Before a hardware trial, verify exact Intel XPU operator and checkpoint-loading support, a supported quantized path and full simultaneous memory envelope; establish whether a reliable structured task interface can be added despite the model's instruction-following limitation. Use synthetic input first, then consented French physical speech, measuring overlap handling and false interruptions. No model weights or new GPU model were downloaded or loaded in this review, and no performance, tool-use, French quality or no-spill claim has been verified locally.

## Intel and cache preflight

The pinned `haru/pyproject.toml` requires PyTorch 2.6 or newer, Transformers 5.16 or newer, and other audio dependencies. A package metadata check of the current `.venv-voice` found `torch 2.15.0`, `safetensors 0.8.0`, and no installed Transformers or `sphn`. A separate lightweight runtime query reported `torch 2.15.0+cpu`, XPU not compiled and unavailable. Thus this existing environment cannot run Haru on the B60 as configured. This does not rule out a separate supported Intel environment; no packages were installed or changed. The repository's optional optimized codec specifically requires CUDA and bfloat16; the plain PyTorch path is available in source but has not been tested on XPU.

The pinned [model configuration](https://huggingface.co/higurashi-ai/Haru-4B/blob/8d6e83bcd3701a76fc27a764965665da1df7da78/config.json) declares eight full-attention layers, four KV heads and head dimension 256. The source constructs Transformers `DynamicCache` without requesting quantization. Assuming two bytes per cached key/value element and one batch, a simple full-attention KV estimate is `8 layers × 2 (K,V) × 4 heads × 256 dimensions × 2 bytes = 32,768 bytes per position`: approximately 141 MiB for 4,500 positions (ten minutes at 7.5 frames/s), or 844 MiB for 27,000 positions (one hour), before prompt positions and other memory. These are arithmetic estimates, not measured allocations: they omit linear-attention state, audio codec state, temporary tensors, allocator overhead and other processes, and actual cache dtype and growth must be checked in the deployed runtime. No quantized KV path was identified in the inspected Haru code.

## Isolated PyTorch XPU smoke test

[Intel's PyTorch 2.14 Windows guide](https://www.intel.com/content/www/us/en/developer/articles/tool/pytorch-prerequisites-for-intel-gpu/2-14.html) lists driver 32.0.101.8801 or later for its verified Arc B-series Windows setup. The B60 on this machine reports 32.0.101.8805 on Windows 11 build 26200. Intel's separate [2.15 guide](https://www.intel.com/content/www/us/en/developer/articles/tool/pytorch-prerequisites-for-intel-gpu/2-15.html) lists 32.0.101.9033 or later; neither general Arc listing by itself certifies this specific configuration. No driver was changed.

Created a separate `.cache/haru-xpu-env` and installed the official `torch==2.14.1+xpu` wheel and its dependencies from the PyTorch XPU index; the existing voice environment was not modified. A separate process reported XPU available, one device named `Intel(R) Arc(TM) Pro B60 Graphics`, BF16 support, and produced the expected sum 128 from an 8×8 XPU tensor operation. NumPy was absent and produced an initialization warning; no Haru dependencies or weights were installed and no model ran. The new environment occupied 4,132,605,880 bytes on disk when measured, excluding the pip download cache. A later whole-system sample after the probe reported 11,299,061,760 bytes dedicated GPU and 202,039,296 bytes shared GPU; this is not a peak measurement or proof of no spill during initialization. The owned demo and existing model servers remained running.

This establishes a minimal XPU execution path on the current machine, not Haru compatibility, Qwen/codec operator coverage, real-time speed, quantization or the total concurrent memory budget. Next verify small representative operators and quantization in the isolated environment before considering checkpoint loading; update dependencies only within that environment and monitor resource use.

## Representative operator smoke test

Installed NumPy 2.4.6 and safetensors 0.8.0 into the isolated environment. `scripts/probe-haru-xpu-ops.py` then compared tiny BF16 1-D convolution, RMS normalization and causal scaled-dot-product attention against CPU BF16 outputs, and loaded a tiny temporary safetensors file directly to `xpu:0`. The final run passed with maximum absolute differences 0, 0 and 0.00390625 respectively, using `atol=0.03` and `rtol=0.03`. PyTorch reported a 5,632-byte peak allocation and 2,097,152-byte peak reserved by its allocator for this process; these are not device-wide or driver peaks. The temporary file was removed by the probe.

The first attempt failed because peak memory statistics were reset before XPU initialization; the probe now initializes first. Two further attempts compared BF16 against FP32 using an overly restrictive absolute threshold and failed on convolution. The final comparison uses the same BF16 input precision on both backends; this tests backend agreement, not FP32 accuracy. The tests use tiny random shapes, not Haru's actual model or all of its Qwen and streaming codec operators. They do not establish speed, sustained memory residency, interruption, quantization or absence of spill.

## Tiny Haru architecture test

Installed Transformers 5.16.1 and the other required audio libraries in the isolated XPU environment, and checked out the pinned Haru source under `.cache`. `scripts/probe-haru-tiny-model.py` constructed a randomly initialized reduced Haru model with one Qwen linear-attention layer, one full-attention layer and a reduced stateful codec. On the B60 using PyTorch 2.14.1 XPU, a prompt prefill, cached next step and two encode/decode frames completed and agreed with CPU BF16 within `atol=0.05`, `rtol=0.1`. Maximum absolute differences were 0.01171875 for prefill and 0.015625 for the cached step; the tiny codec outputs matched in this run. PyTorch reported a 649,728-byte process allocator peak; this is not a device-wide peak.

This executes selected actual implementation paths with randomly initialized tiny tensors, no checkpoint, no tokenizer, no complete live conversation and no audio device. It does not validate full-size dimensions, numerical fidelity of trained weights, speed, structured tools, quantization, long context or the complete system's memory budget. The source checkout and isolated packages remain in `.cache` for reproducibility.

## Small INT4 backbone experiment

Installed `torchao==0.18.0+xpu` in the isolated environment with `--no-deps`, retaining PyTorch 2.14.1 XPU. The first `Int4WeightOnlyConfig` attempt used torchao's default packing and failed before inference because it required `mslk`; no success is claimed for that path. Inspection of the installed implementation identified its `plain_int32` oneDNN XPU path. With `--int4`, the tiny-model probe uses that packing, group size 32 and only eligible backbone linear layers. Fifteen layers were represented as `Int4PlainInt32Tensor`, and prefill, a cached step, and the unchanged tiny codec executed on the B60. Compared with the unquantized XPU BF16 output, the maximum absolute differences were 0.2578125 for prefill and 0.240234375 for the cached step; outputs were finite, but no accuracy threshold was asserted. PyTorch reported 887,296 bytes peak allocated for the whole tiny process, not device-wide memory or an INT4-only footprint.

This checks a low-bit execution path on random small shapes; it is not evidence of acceptable French or tool quality, real-time performance, or full-model support. It quantizes only eligible `nn.Linear` layers in the backbone, leaving embeddings, logits, audio projections, codec, head and KV cache outside that claim. The experiment creates a BF16 GPU model first and then quantizes it, so its loading strategy would not enforce a full-model peak-memory limit. No checkpoint was loaded. A practical full-model test needs a bounded low-peak loading strategy, verified cache precision, model-level quality tests and controlled whole-system memory measurements.

## Full-checkpoint header estimate

`scripts/inspect-haru-tensors.py` fetched the pinned configuration and safetensors header, then constructed the full architecture on PyTorch's `meta` device without loading checkpoint weights. The header lists 1,022 BF16 tensors totaling 10,540,001,798 payload bytes. Matching the same backbone linear-layer selection used in the tiny test found 248 weight tensors, with 3,569,090,560 eligible parameters. The remaining tensors account for 3,401,820,678 BF16 payload bytes. Each selected name and shape was checked against the header, but group-size divisibility does not prove every full-size tensor is accepted by the XPU kernel.

An ideal packed INT4 payload for those selected weights is 1,784,545,280 bytes; adding 334,602,240 bytes for one assumed BF16 scale and INT8 zero per 32 weights yields 5,520,968,198 bytes including the remaining BF16 tensors. This is a lower-level arithmetic estimate, not a measured size or load plan. It excludes tensor and kernel padding, duplicated or tied weights, transient BF16 copies, allocator and driver overhead, model caches, audio state and all other services. The implementation must confirm actual metadata dtypes, avoid the original full-BF16 GPU load and enforce the requested budget before any full checkpoint trial. No weights were downloaded and no XPU model was created for this header inspection.

The inspected full architecture and header have matching persistent state-key sets. The largest single BF16 tensor is the unquantized token embedding at 1,271,398,400 bytes, so even a per-tensor loader has nontrivial transient and resident memory requirements.

## Tiny streamed-loading prototype

`scripts/probe-haru-streamed-load.py` creates a tiny synthetic BF16 safetensors checkpoint, constructs the same reduced architecture on the meta device, then assigns one tensor at a time and converts eligible backbone linear weights to the XPU INT4 format. It rejects mismatched state keys, shapes, dtypes and parameter aliases. The first attempt detected non-persistent meta buffers that are absent from the checkpoint: rotary frequencies and the audio head's scalar frequencies. The probe now explicitly reconstructs those buffers and rejects any remaining meta tensors.

The final tiny run quantized 15 layers and matched the existing full-BF16-then-quantize reference in prefill, cached step, codec encode/decode and head output within `atol=0.01`, `rtol=0.01` (maximum observed differences zero). The largest tiny BF16 tensor was 16,384 bytes and PyTorch's process allocator reported a 240,640-byte load peak. A deliberately oversized synthetic file was rejected by an 8 MiB probe limit. These are tiny synthetic checks, not a complete full-model loader, proof of bounded device-wide peak, no paging, model quality or speed. Memory mapping, driver allocations, packed-layout padding, kernel behavior at full shapes, native state and concurrent services remain unmeasured. The full checkpoint was not downloaded or loaded.

## First real-dimension INT4 layer

The header analysis found seven distinct eligible linear shapes. `scripts/probe-haru-int4-shape.py` tests only the smallest, 32×2,560, which occurs 48 times in the checkpoint; it creates random BF16 weights and input, quantizes with the XPU `plain_int32` group-32 path and executes one output. On this B60 it produced finite output. The maximum and mean absolute differences from the unquantized BF16 output were 0.08313 and 0.03473; no model-accuracy criterion was asserted. PyTorch's allocator reported 840,192 bytes peak allocated and 2,097,152 bytes peak reserved, excluding driver and other-process allocations. No checkpoint or audio was loaded.

The six larger checkpoint shapes, full model and concurrent peak remain untested. The script intentionally does not accept larger dimensions until an appropriate whole-system watchdog is in place. A passing isolated linear operation is not evidence that the full model runs, remains in VRAM, produces intelligible French or can call tools.

## Guarded larger-shape attempt

Prepared `scripts/run-haru-int4-shapes.ps1` to run the other six pinned shapes separately, monitoring global B60 dedicated and shared memory, available RAM and both existing inference slots. Its limits are 18 GiB dedicated, 256 MiB shared and at least 8 GiB available RAM during execution, with 10 GiB RAM required at preflight. These are sampled thresholds, not a hard memory cap; allocations between samples can exceed them.

The first larger-shape attempt, 1,024×2,560, was stopped after the watchdog reported a resource threshold violation. The first version failed to write the violating sample or specify the threshold, so the cause and exact observed peak are unknown. Seven preceding samples showed maximum dedicated 11,601,588,224 bytes, maximum shared 205,135,872 bytes and minimum available RAM 13,596,467,200 bytes. No passing result was produced; the other five shapes were not attempted. The script now writes each sample before checking it and identifies the threshold. Cleanup was also changed to terminate the started Windows process tree because a venv launcher can spawn the actual Python interpreter. PowerShell parsing passed; the changed watchdog and cleanup path have not yet been exercised in another real run. The user-requested no-spill constraint remains unproven, so the test was not immediately repeated.

The revised watchdog was then exercised with `-SmokeOnly`, which uses the previously tested 32×2,560 synthetic layer. It returned failure because sampled **whole-system shared GPU usage reached 282,312,704 bytes**, above the 256 MiB threshold, from a 204,087,296-byte initial sample. The last sample also reported dedicated usage 11,692,240,896 bytes and available RAM 11,836,837,888 bytes. The layer's JSON output was present, but the guard's failure means this is not a passing guarded run. The samples do not identify which process or allocation caused the increase, and shared GPU usage is not proof that model weights spilled; the roughly one-second sampling also cannot capture every peak. The process-tree cleanup reported that a child had already exited during termination; no matching probe Python process remained when checked. The runner now suppresses that benign taskkill race message, but this last cleanup change has not been exercised. The larger INT4 shapes and full model were not retried. Further XPU work requires understanding or reducing the shared-memory baseline and attribution before drawing a no-spill conclusion.

## Process-counter attribution preparation

Windows exposes GPU Process Memory counters by process and adapter. A read-only live check of the existing agent model process reported 8,129,933,312 bytes dedicated and 30,425,088 bytes shared for the B60 at one instant. These are WDDM accounting observations, not evidence of where a particular tensor resides. [Microsoft notes](https://devblogs.microsoft.com/directx/gpus-in-the-task-manager/) that per-process GPU counters can include cross-process shared allocations, so summing them can double-count; [Microsoft also documents counter inaccuracies in some configurations](https://learn.microsoft.com/en-us/troubleshoot/windows-client/performance/gpu-process-memory-counters-report-wrong-value).

The shape watchdog now records matching dedicated and shared counters for the probe process tree only, alongside its existing whole-adapter sample. Counter collection reports `not_observed` or `unavailable` rather than treating absent data as zero. A Windows test with synthetic counter instances checks that other process IDs and adapters are excluded; a read-only check against the existing agent process returned its counters. Process enumeration and GPU samples are not atomic and can miss short-lived children, so this does not explain the earlier spike or establish a no-spill guarantee. No further XPU workload was started for this change.

## Import control and held small-XPU comparison

With the baseline shared GPU counter reduced to 137,633,792 bytes, `scripts/run-haru-int4-shapes.ps1 -ImportOnly` imported the same libraries, requested no XPU initialization or tensor operation, and held for four seconds. Across its samples, the adapter shared counter remained at 137,633,792 bytes; no probe-process GPU counter was observed. This is one control, not proof that imports can never initialize GPU resources.

The smallest synthetic 32×2,560 INT4 operation was then repeated with `-SmokeOnly`, holding its process for five seconds after output so its GPU counters could be sampled. The guard completed without crossing its configured thresholds. During the hold, one probe-process instance reported 523,747,328 bytes dedicated and 78,225,408 bytes shared; the adapter shared counter rose from 137,633,792 to 215,859,200 bytes. The corresponding adapter dedicated sample was 11,660,263,424 bytes, and the later observed peak during the short run was 11,670,495,232 bytes. The process-attributed shared value matches the observed adapter increase in this run, which is consistent with the XPU process contributing to it; these counters are not a tensor-level residency trace, can contain shared allocations and are not atomic. The final sample's process counters were unavailable after the process ended. PyTorch's reported peak tensor allocation was only 840,192 bytes, demonstrating why its allocator metric alone is insufficient for the complete runtime footprint.

This explains neither the specific allocations nor whether trained model weights would reside outside VRAM. The sampled operation remained below the selected absolute shared threshold on this lower baseline, unlike the earlier run, but this is not proof of no spill, a hard 24 GB cap or full-model viability. Larger shapes and Haru weights remain untested.

## Larger shape retry under the guard

The next guarded 1,024×2,560 synthetic layer attempt started after a preflight sample of 204,087,296 bytes whole-adapter shared GPU usage. The layer produced finite INT4 output, with maximum and mean absolute differences of 0.118164 and 0.028431 from its synthetic BF16 reference. No model-quality threshold was asserted. PyTorch reported 26,715,136 bytes peak tensor allocation and 33,554,432 bytes reserved, excluding other runtime and driver allocations.

The guard returned failure because its last sample reported 280,215,552 bytes whole-adapter shared usage, exceeding the 256 MiB absolute threshold. The probe's process counters were unavailable at that sample, so this observation does not establish allocation ownership or the residency of weights. A later demo status sample showed shared usage back at 204,087,296 bytes. The remaining five larger shapes were not run. The fluctuating starting baseline shows why the prior small-shape pass cannot be generalized. No model checkpoint or physical audio was used, and the full memory/no-spill requirement remains unproven.
