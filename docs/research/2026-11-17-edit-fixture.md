# Disposable coding demonstration — 2026-11-17

## Hypothesis and setup

An explicitly approved coding task against a separate disposable fixture could demonstrate a real file edit while leaving the existing read-only session in place. It would not establish general coding ability, production safety or OS-level isolation. The installed OpenCode reports version 1.19.5; its V1 permission format is documented in the [V1 permissions documentation](https://opencode.ai/v1/docs/permissions/). Current OpenCode documentation describes a different V2 configuration format, so it should not be assumed applicable to this installed binary.

The existing `scripts/setup-agent-edit-probe.py` created `.cache/agent-edit-demo` without overwriting an existing directory. Its initial `calculator.py` returns subtraction in `add(a, b)`. `scripts/start-windows-harness.ps1 -EditFixture` started a separate OpenCode server on loopback port 18110. The checked configuration uses the existing local Gemma server, permits read, glob, grep and edit, denies external directories, and denies unspecified actions. These are application-level permissions, not an operating-system sandbox; arbitrary local processes can still reach the unauthenticated server.

`scripts/start-windows-demo.ps1 -Port 18111 -EditFixture` started a separate volatile gateway with explicit task approval, the existing models and a shared advisory reservation ledger. The browser now displays an operator-supplied workspace label; it is descriptive and does not independently verify the harness configuration. The startup sample reported 11,459,932,160 bytes dedicated GPU, 178,286,592 bytes shared GPU and 17,890,672,640 bytes available RAM. Sampling and admission do not enforce a hard GPU or host-memory limit. The existing read-only gateway and harness were not stopped.

The live harness configuration endpoint and fixture contents were inspected. Five targeted JavaScript tests passed, including a mock-gateway approval flow and simulated browser label display; two fixture-setup Python tests passed and PowerShell scripts parsed successfully. A separate live user-approved edit has been requested but was not observed at this checkpoint. The test requires checking the exact proposal and permitting only the disposable fixture task. Web search, general workspace selection, true sandboxing, physical speech and long-running memory residency remain unverified.

`node scripts/probe-edit-proposal.mjs` then sent a synthetic typed request through the real controller and gateway. The displayed proposal, reviewed by inspection, preserved `calculator.py`, the `add` function, the change from subtraction to addition and the restriction to one file. The probe explicitly declined the proposal, observed a completed response and 470,400 audio bytes, and did not listen to the output. The fixture still contained subtraction afterwards and the harness status endpoint reported no busy session. A later snapshot reported 11,514,474,496 bytes dedicated GPU, 179,122,176 bytes shared GPU and 15,734,308,864 bytes available RAM; it is not a peak measurement. This validates one real proposal and decline, not approval, task execution, a physical voice request or general semantic reliability.
