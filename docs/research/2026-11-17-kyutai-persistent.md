# Persistent Kyutai CPU experiment — 2026-11-17

## Question and protocol

Can retaining the quantized Kyutai STT model in memory reduce the buffered sidecar's latency without harming French recognition or exceeding the observed resource guard? The [pinned CrispASR server documentation](https://github.com/CrispStrobe/CrispASR/blob/1694d8ef516799b290c6da5fe80803b4af2771b0/docs/server.md) describes a persistent model and an HTTP transcription endpoint. This is an author claim, not evidence that this specific backend and model perform correctly. The experiment uses the previously hash-verified Q4 model, CrispASR v0.8.53 Windows CPU binary, Pocket TTS synthetic French audio and one second of trailing silence. No physical devices are opened.

Run `./scripts/run-asr-coding-probe.ps1 -PersistentTrial -ProcessMetrics` on the configured Windows machine. The original probe sent the same generated waveform to the existing file-mode implementation and twice to a temporary localhost server, then stopped its own process. The current version replaces the second server request with the rate-mismatch control described below. It requests seed 42 and disables fallback in the CLI; HTTP requests additionally specify seed 42 and temperature zero. These controls do not establish equivalent decoding across the two code paths. The server is started without warmup. The timing of file mode includes process and model load; server request timings exclude startup. Each separate trial generates fresh synthetic audio, so compare text within a trial, not as a paired comparison across trials.

The wrapper requires at least 8 GiB available RAM before starting and samples system memory and GPU usage while running; it requests termination if available RAM drops below 6 GiB, dedicated GPU exceeds 22 GiB, or shared GPU exceeds 256 MiB. Sampling can miss transients and cannot establish an absence of paging or GPU spill. Optional process metrics sample descendant working set and private bytes, which are neither total system cost nor proof of model residency. Process enumeration itself can affect timings. The probe writes temporary audio for file mode and the server may create its own temporary files; abnormal termination may leave artifacts. Local network isolation was not independently verified.

## Decision and next experiment

The persistent requests were faster in these observations, but two trials corrupted the arithmetic and the controlled-seed trial produced unusable byte-like output. This is insufficient for a user-facing replacement; the gateway retains its current recognizer. Causes such as different defaults, request handling, decoder state or a backend bug remain hypotheses. Inspect the pinned implementation's request and file decoding paths, reproduce with a fixed retained non-personal fixture and matched parameters, then test diverse French voices, noise and interruption before considering integration. These tests do not validate physical audio, real-time streaming, full duplex or the full 24 GiB no-spill requirement.

## Sample-rate hypothesis and targeted test

Inspection of the pinned v0.8.53 source reveals a concrete discrepancy: the [HTTP server](https://github.com/CrispStrobe/CrispASR/blob/1694d8ef516799b290c6da5fe80803b4af2771b0/examples/cli/crispasr_server.cpp#L565-L568) decodes uploads with the default 16 kHz rate and later [passes those samples to the backend](https://github.com/CrispStrobe/CrispASR/blob/1694d8ef516799b290c6da5fe80803b4af2771b0/examples/cli/crispasr_server.cpp#L830); the [Kyutai adapter](https://github.com/CrispStrobe/CrispASR/blob/1694d8ef516799b290c6da5fe80803b4af2771b0/examples/cli/crispasr_backend_kyutai_stt.cpp#L30-L41) expects 24 kHz. The [file-mode dispatcher](https://github.com/CrispStrobe/CrispASR/blob/1694d8ef516799b290c6da5fe80803b4af2771b0/examples/cli/crispasr_run.cpp#L997-L1001) explicitly loads at the backend's native rate. These source observations support a sample-rate mismatch; they do not alone prove it caused every previous failure.

To discriminate the hypothesis, the revised probe synthesizes one short utterance, sends its original PCM to file mode and the server, then resamples the same PCM from 16 to 24 kHz but deliberately labels that control WAV as 16 kHz for a second server request. This experimental relabeling makes the sample count seen by the backend approximate the expected rate, but makes server-side duration, timestamps, slicing and other processing wrong. It is strictly a research control, not a production workaround. The control uses SciPy's `resample_poly`; its resampler is not guaranteed identical to file-mode decoding.

The guarded run `.cache/asr-coding-20261117-224745-485.*` returned file-mode `combien font deux plus trois réponds en un mot` in 3,172 ms including load; the original server upload returned `oh yeah from derby club i have one` in 2,079 ms; the rate control returned `combien font deux plus trois réponds en un mot` in 2,718 ms. Startup to health was 515 ms. Peak sampled dedicated GPU was 12,382,830,592 bytes, peak shared 260,751,360 bytes, and minimum available RAM 10,051,190,784 bytes. This single synthetic phrase strongly supports the mismatch hypothesis, but does not establish broad accuracy or account for unsampled transients. A proper correction must make HTTP decoding, slicing and timestamps agree with each backend's actual rate, with regression coverage across backends; then it requires fresh realistic speech and resource tests before integration.

## Native-rate patch under evaluation

A local experimental [patch](crispasr-server-native-rate-experiment.patch) against source commit `1694d8ef516799b290c6da5fe80803b4af2771b0` keeps the server's 16 kHz slicing and time base, resampling each slice to the backend's native rate before the main transcription call. It uses CrispASR's own polyphase resampler. This does not address every path: in particular, gap-fill and real-time streaming have separate calls that must be audited. It is not approved as a general fix, and has not yet been compiled or tested.

The source and pinned submodules were checked out under ignored `.cache/crispasr-source`. Windows configuration succeeded with Visual Studio 2022 MSVC 19.44, CMake and Ninja, Release mode, CPU only, tests disabled, OpenMP off and `GGML_NATIVE=OFF`. A single-worker build of `crispasr.exe` was running at this checkpoint; no inference result can be inferred from that build. The first configuration failed because the required `c2pa-audio` submodule was missing; initializing that pinned submodule resolved configuration. Once the build finishes, check its actual exit status, run the same-audio probe against the built binary, then verify timestamps, long slices, gap-fill, other backend rates and memory before integration. The existing demo remains on its original binary.

Source inspection shows that Kyutai inherits the default zero `vad_slice_cap_seconds`, so the HTTP gap-fill branch is not selected for this backend in the inspected version. Other backends can select it and the patch does not convert its input; consequently the patch must not be treated as a general solution. The HTTP streaming branch and separate real-time server call `transcribe_streaming` independently and are not patched. No real-time behavior is established by this experiment.

The wrapper now supports `-PersistentTrial -ProcessMetrics -LocalCrispBuild`, selecting only the expected local build path and tracking that executable's descendant processes for metrics and cleanup. This option has only been unit-tested indirectly and must not be run until the build succeeds. The original upload is the meaningful case for a corrected server: the deliberately mislabeled rate-control upload would then be incorrect. The wrapper's usual sampled resource guards still apply.

For a paired comparison across separate runs, `-FixedSyntheticFixture` makes the probe generate the fixed Pocket TTS math phrase once under ignored `.cache/kyutai-persistent-synthetic-math.wav`, reuse that file in subsequent runs and report its SHA-256.
