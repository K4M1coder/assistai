# Toward a Local French Voice Agent on a 24 GB GPU: An Experimental Study

**Working draft — incomplete.** This document synthesizes selected experiments; it is not a claim that the requested system, final evaluation, or strict memory budget has been achieved. Detailed protocols, commands, timestamps and contradictory observations remain in the linked research records.

## Abstract

We investigate a local conversational voice assistant that can delegate coding tasks while remaining responsive on a Windows system with an Intel Arc Pro B60 and a 24 GB dedicated-memory target. The working demo uses a French Vosk recognizer, an LFM3-1.7B Q8 text controller, Pocket TTS, a Gemma 4 12B Q4 agent model and an OpenCode harness. This is a speech-text-speech cascade. A separate experimental LFM3-Omni native speech path twice delegated a synthetic French read-only request to a real local agent and produced result notification audio; independent recognizers disagreed on that audio. A separate cascade loopback answered a capital question but failed an arithmetic question after recognition changed its meaning. A CPU Kyutai STT experiment exposed a reproducible sample-rate mismatch in a particular HTTP server version. Correcting the experimental server improved two synthetic examples, but a natural French voice produced an empty transcript at original level and an inaccurate transcript after gain. Results are exploratory, not a benchmark or evidence of full-duplex operation, general reliability, or absence of memory spill.

## Objective and architecture

The intended system accepts and generates French speech, supports interruption in both directions, shares task context with a capable coding and image-understanding agent, and executes locally on Windows and Linux. Intel Arc is the first target; NVIDIA and AMD portability remain later requirements. All model weights, context and concurrent workloads must fit the user's 24 GB VRAM constraint without model spill to RAM or SSD. The prototype currently exposes a local browser client and gateway, with distinct speech recognition, text reasoning, speech synthesis and agent services. OpenCode runs against an explicitly configured disposable workspace. The gateway delegates directly at the operator's request; application permissions are not an operating-system sandbox. The separate React interface is a mockup and is not evidence of production capabilities. See [architecture](../ARCHITECTURE.md) and [RBAC](../RBAC.md).

An alternative native audio-and-vision candidate, LFM3-Omni-2B Q4 with official Q8 and F16 projectors, was subsequently loaded under sampled Windows resource guards. Its [publisher's model card](https://huggingface.co/LiquidAI/LFM3-Omni-2B) describes French speech, image input and speech output; its [GGUF instructions](https://huggingface.co/LiquidAI/LFM3-Omni-2B-GGUF) describe a realtime WebSocket and tool calling. These claims do not establish simultaneous listening and speaking. On a synthetic French question the local model produced correct text, but generated audio was sometimes truncated and independent transcriptions did not reliably match. A narrow read-only agent workload has been exercised concurrently; sustained agentic workloads remain untested. See the [candidate record](2026-11-17-lfm3-omni-candidate.md).

## Method

Experiments record the hypothesis, local configuration, commands, observations and limitations. Fixed synthetic French audio allows repeatable input without a physical microphone. For output checks, a separately loaded recognizer transcribes generated audio; agreement is an imperfect proxy for human intelligibility. Natural-speech checks use attributed, hash-verified French [FLEURS](https://huggingface.co/datasets/google/fleurs) fixtures, rather than private recordings. Small samples are diagnostic only. Windows WDDM dedicated/shared GPU counters and available RAM are sampled around selected trials; the watchdog can terminate owned processes, but sampling misses transients and is not an allocation guarantee or proof against paging. Experiments distinguish real model execution, user-reported observations and simulated tests.

## Results

In one direct-delegation test, the controller started an OpenCode task on a disposable `calculator.py`, generated a separate follow-up while it ran, and reported completion after 21,014 ms. An independent AST check found `return a + b`; notification audio was generated but not transcribed in that test. No complete peak-resource trace was retained. In a separate synthetic audio loopback, a capital question produced the correct text answer and a similar independent output transcription; a mathematical question failed because the input recognizer changed the request. These are different tests, not one validated voice-to-edit scenario. See [direct delegation and loopback](2026-11-17-direct-delegation-audio-loopback.md).

The native model additionally identified two synthetic solid-color images and proposed a tool call from a synthetic French spoken request. In two separate guarded runs, a temporary native gateway delegated a spoken fixture-reading request to a real read-only OpenCode harness, received the correct `BLUEBIRD` result and produced a spoken notification. The optional Vosk input transcript misstated the filename although the actual tool request contained it. For one saved notification Kyutai transcribed a phonetic `blue bird` while Vosk did not recover the word. Across the two 120-second system traces, peak sampled dedicated GPU use was 13,553,860,608 bytes, peak shared 243,298,304 and minimum available RAM 12,571,840,512; individual events were not precisely aligned to samples. This is evidence for one narrow native speech-to-agent path, not human intelligibility, general coding, simultaneous conversation, full duplex or a no-spill guarantee. See the [native candidate record](2026-11-17-lfm3-omni-candidate.md).

The pinned CrispASR v0.8.53 HTTP path was found to decode at 16 kHz while its Kyutai adapter expected 24 kHz. On identical synthetic input, a local experimental patch that resamples each HTTP slice recovered the reference phrase where the released server failed. A deliberately mislabeled rate-control input reversed the outcome. On one natural male-voice fixture, both file and HTTP modes returned empty text at original level; an eightfold non-clipping gain produced a materially inaccurate transcript. A second natural female-voice fixture was largely recognized even at a lower overall RMS, so level alone cannot explain the difference. On that second sample, one sequential comparison measured patched HTTP at 6.36 s with four CPU threads versus 8.11 s with two. Neither a few utterances nor uncontrolled timings establish general accuracy or realtime suitability. See [persistent Kyutai experiments](2026-11-17-kyutai-persistent.md).

User reports include understandable French speech and one successful manual interruption, alongside earlier reports of cut-off speech, self-interruption through speakers and unreliable noise handling. These reports are valuable observations, not controlled full-duplex or acoustic measurements. The speaker-safe mode prevents voice barge-in during playback; experimental echo suppression remains unreliable. Exact conditions and earlier failures are preserved in the [research index](README.md).

Headless Chrome tests used a synthetic fake microphone and muted output with speaker-safe disabled. A repeated spoken fixture interrupted scheduled native-model audio and was followed by the correct capital answer and further audio; because the questions were identical, this did not exclude a stale answer. A different arithmetic follow-up interrupted audio but produced an unavailable-agent response. After the bridge stopped advertising delegation without an agent, the same synthetic arithmetic voice produced an incorrect `3`; a different Windows-synthesized voice produced the correct calculation after interruption. These limited unseeded examples do not isolate the cause and are not acoustic echo tests, evidence of the model interrupting the user, or proof of full duplex. Sampled resources and exact conditions are in the [candidate record](2026-11-17-lfm3-omni-candidate.md).

Two later runs using that Windows-synthesized follow-up produced the text `2 plus 3 font 5.` after interruption; an independent CPU recognizer returned the same words from each captured browser-scheduled audio stream. The first run's strict check falsely rejected digit-form operands and was corrected before the second run, which passed. Capturing scheduled buffers is not equivalent to recording physical playback, and this small repeated synthetic case does not establish human intelligibility or general reliability. The detailed record includes the original failure and resource samples.

In a subsequent synthetic browser test with a real read-only agent task, a two-second gap separated a fixture request from a capital question. The second utterance interrupted the assistant during the task and received the correct capital answer, but the agent returned a question rather than the fixture word and the generative task notification incorrectly claimed the secret was Paris. This fails the combined task objective and shows that a fluent notification cannot be assumed faithful to the agent result. The [candidate record](2026-11-17-lfm3-omni-candidate.md) preserves the unsuccessful no-gap control and resource observations.

## Limitations and next work

The native candidate needs reliable generated speech and broader image and tool-call trials measured alongside the agent under representative concurrent load. A later headless Chrome run used a synthetic microphone, delegated a real fixture read and captured its explicit spoken notification, but two recognizers did not faithfully transcribe the French output. This does not establish human intelligibility or full duplex. The HTTP sample-rate patch needs broader natural and noisy speech, timestamp, long-slice and regression testing before integration. Reliable speaker barge-in, physical playback quality, agentic vision and coding breadth, Linux portability, failure recovery and full 24 GB no-spill verification remain open. The current advisory accounting and sampled guard do not enforce the user's hardware invariant. Reproducible setup and teardown must be validated from a clean environment, and benchmark data must retain their source licenses and attribution. The final paper must be revised against that evidence rather than extrapolating from these preliminary cases.
