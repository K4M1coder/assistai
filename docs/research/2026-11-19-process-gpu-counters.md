# Process-level GPU memory observations on Windows

## Hypothesis and sources

Per-process GPU counters may help identify which inference servers contribute to shared GPU memory, supplementing the existing whole-adapter watchdog. They cannot identify individual model weights or prove physical residency. Microsoft's [DXGI memory information](https://learn.microsoft.com/en-us/windows/win32/api/dxgi1_4/ns-dxgi1_4-dxgi_query_video_memory_info) describes an application's current usage and OS budget, not the contents of its allocations. [WDDM residency documentation](https://learn.microsoft.com/en-us/windows-hardware/drivers/display/driver-residency-in-wddm-2-0) describes process residency budgets and their variability. A single sample is not a bound on past or future allocations; even sustained sampling can miss transients. PID reuse, subprocesses, shared allocations and OS accounting further limit attribution.

## Local observation

On 2026-11-19, `Get-Counter -ListSet 'GPU Process Memory'` listed per-process dedicated and shared usage counters on this Windows machine. `& .\scripts\snapshot-gpu-process-memory.ps1 -ProcessId @(60860,34416)` sampled the current adapter instance. The model server on port 18080, PID 60860, reported 7,959,998,464 dedicated and 30,425,088 shared bytes. The text controller on port 18084, PID 34416, reported 1,998,295,040 dedicated and 14,204,928 shared bytes. Both were existing llama.cpp processes; commands and model configuration were inspected locally. The script also records process start times to aid identification. This is one idle snapshot, not a concurrent workload measurement or proof that model weights or context spilled to RAM. Shared usage can include buffers and driver allocations, so its presence alone does not classify those bytes.

The script requires explicit process IDs and adapter instance, rejects invalid IDs and missing or ambiguous counter instances, and is read-only. Local checks confirmed that a negative PID and an absent GPU counter are rejected. It does not track PID identity continuously, collect every child process, enforce a memory limit, or prove that Windows did not page allocations. The specific PIDs and adapter identifier are machine-specific and can change after restart. Do not silently treat a missing counter as zero.

`scripts/sample-gpu-process-memory.ps1` now repeats that snapshot while checking that each process retains its initial start time; it stops if a counter disappears or an identity changes, and refuses an existing output filename. An initial local smoke test mistakenly reported an identity change because PowerShell converted the JSON timestamp to a date; comparing UTC ticks corrected that false alarm. A subsequent four-second idle smoke test recorded four samples. Neither test demonstrates a hard resource limit.

On 2026-11-19, a 60-second run, `& .\scripts\sample-gpu-process-memory.ps1 -ProcessId @(60860,34416) -RunId agent-task-20261119-2202 -Seconds 60`, collected 59 samples while `node scripts/probe-native-pocket-notification.mjs --real-agent` used a real read-only OpenCode fixture and local Pocket TTS. That probe returned the expected `BLUEBIRD` text and 201,600 bytes of 24 kHz notification audio. Its native voice model was simulated; the audio was not saved or listened to. Across all 59 samples (`.cache/assistant/gpu-process-agent-task-20261119-2202.jsonl`), the agent model server reported 7,959,998,464 dedicated and 30,425,088 shared bytes in every sample; the separate controller reported 1,998,295,040 dedicated and 14,204,928 shared bytes. This interval included the task but did not precisely timestamp its start and finish within the samples. The controller was not used by this simulated-native probe. The owned harness was stopped after reporting idle. These counters do not identify model-resident data, enforce a cap or exclude missed peaks and paging; no native voice model was loaded concurrently.

In a subsequent guarded real-native trial on 2026-11-19, `node scripts/probe-native-browser-barge-in.mjs --agent-fixture --agent-gap-ms=2000 --agent-tts --capture-run-id=agent-tts-20261119-2204` used real native speech, the real read-only agent and Pocket TTS with muted headless Chrome and synthetic microphone input. It detected interruption while the task was active and correctly answered the capital question, but exited 1 after its polling window without observing task completion or a notification. After the probe's temporary gateway closed, the harness reported idle; its session record showed a final assistant step with finish reason `length` and no final text. This is evidence of an incomplete task, not a successful answer, and the timing does not establish that the gateway would necessarily have reported that terminal condition before the probe closed. The owned harness was stopped only after the idle check.

The independent process observer was started after native readiness and recorded 73 samples (`.cache/assistant/gpu-process-native-agent-20261119-2204.jsonl`) for agent PID 60860 and native PID 1292. Agent dedicated/shared counters stayed at 7,959,998,464 / 30,425,088 bytes; native dedicated ranged 2,419,101,696–2,493,845,504 and shared 12,271,616–102,416,384. The observer exited 1 on a performance-counter error near the end, rather than inventing zero values; the time-limited native watchdog subsequently stopped its server. Whole-system watchdog samples (`.cache/assistant/lfm3-omni-idle-20261119-220346-357.*`, 105 samples) peaked at 13,610,213,376 dedicated and 223,981,568 shared, with minimum available RAM 11,509,682,176. These independently timed samples cannot be precisely aligned to task phases, prove weight placement or exclude unobserved peaks. Pocket TTS and Vosk use system RAM.

The browser probe now supports a bounded `--wait-seconds` from 10 to 90 and exits its polling loop on a displayed gateway error; its default remains 50 seconds. This allows a later trial to observe a terminal failure rather than disconnecting solely at the shorter diagnostic window. Syntax, capture, answer-check and agent-status tests passed; the longer wait has not yet been exercised with real inference. The gateway already treats an idle agent's `length` finish as an error rather than a completed task, but the previous trial did not observe the gateway report it before the temporary client disconnected.

On 2026-11-20 the guarded native preflight was refused: shared GPU memory was 207,937,536 bytes and available RAM 9,808,613,376 bytes, beyond both preflight limits. No native model was started. Independently, `node --test prototype/native-truncated-agent.integration.test.mjs prototype/agent-task-status.test.mjs prototype/client-mode.test.mjs` passed five tests. The new integration test runs the actual gateway with simulated native and agent services; an idle agent response ending with `length` and no final text produces `task.error` and no `task.completed`. A simulated client test verifies that this error appears in the activity display and conversation log. These tests do not reproduce the real model's timing, resource use or speech.

## Next experiment

Capture these counters alongside whole-adapter telemetry during an owned, guarded real native voice-and-agent trial, recording process identities and task timing. Compare deltas rather than assuming all shared usage is model memory. Stronger evidence of tensor allocation and residency requires backend-specific tracing and still may not establish a hard no-spill guarantee under all conditions.
