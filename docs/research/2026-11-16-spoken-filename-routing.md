# Spoken filename and task routing — 2026-11-16

## Observation

The operator reported that a French request to read `fixture.txt` was transcribed with a distorted filename. The controller said it could not access the misrecognized file and asked for clarification; spelling it aloud produced another incorrect transcript. No agent task was proposed in the reported exchange. This is physical user feedback, not a controlled ASR benchmark. Previous EXP-185 independently documented identifier errors in synthetic French coding speech.

## Targeted local comparison

Hypothesis: making the tool description explicitly mention file reads may prevent the controller from saying it cannot inspect a file, without introducing unsafe filename guesses. `node scripts/probe-file-routing.mjs` sends synthetic text directly to the already loaded LFM3-1.7B Q8 llama.cpp server on loopback. It uses temperature zero and does not execute any tool calls. The first run compared the existing prompt with a file-aware version on three examples: an exact `fixture.txt` request, the observed distorted filename and a greeting. The exact request produced one `delegate_task` call with `fixture.txt` in both variants, and the greeting produced an ordinary answer in both. On the distorted filename, the existing prompt asked for clarification, while the file-aware prompt proposed reading a file with that distorted literal name.

The second run used `PROBE_VARIANT=file-aware-clarify` to add instructions to ask for an exact filename when it is unclear. It again routed the exact name and did not delegate the greeting. On the distorted filename, however, the model proposed a task that introduced possible `.txt` and `.fixed` extensions. The stronger prompt did not reliably prevent guessing in this one case. This experiment is a small synthetic routing comparison, not an ASR test, semantic benchmark or guarantee about other prompts, temperatures or conversation histories. No returned tool was executed and no new model was loaded.

## Decision and practical workaround

Do not adopt either file-aware prompt on this evidence: they can turn an uncertain transcript into a misleading task proposal. The current prototype already has **Review speech before sending**, which allows the operator to correct the transcript to `fixture.txt` before submission, or the request can be entered directly in the text field. If a task is proposed, the original and proposed requests must still be checked before clicking approval. An exact typed request elicited a file-read proposal in this isolated probe; a physical voice-to-approved-agent completion remains unverified. This workaround does not solve spoken spelling, ASR quality or general task routing.

## Same-audio recognizer comparison

The existing [CrispASR v0.8.53](https://github.com/CrispStrobe/CrispASR/releases/tag/v0.8.53) CPU binary and the [French FastConformer GGUF](https://huggingface.co/cstr/stt-fr-fastconformer-hybrid-ctc-large-GGUF) were already installed and previously described in EXP-152 and EXP-155. The publisher labels the model CC-BY-4.0; model conversion and runtime licensing should be reviewed independently before distribution. The hypothesis was that the candidate might better retain the reported filename, not that it would necessarily be a better streaming recognizer.

`scripts/run-asr-coding-probe.ps1 -CompareCrisp -FixtureOnly` generated two new synthetic phrases with the running French Pocket TTS and fed the identical PCM to Vosk and the CPU candidate. For the naturally spoken filename phrase, Vosk produced `fixe turpin texte` while FastConformer produced `fixture text`. Both had normalized WER 0.182 against the spoken phrase, but neither produced the exact filename `fixture.txt`. For the spelled phrase, Vosk's normalized WER was 0.357 and FastConformer's was 0.857; neither reproduced the full spelling. These are two synthetic phrases from one voice, not user speech or a representative language benchmark. Vosk's measured times included paced audio transmission to an already loaded service; the candidate's included a fresh process and model load, so they are not comparable end-to-end latency measurements.

The guarded comparison completed with 13 whole-system samples, maximum dedicated GPU 11,471,593,472 bytes, maximum shared GPU 124,481,536 bytes and minimum available RAM 16,114,847,744 bytes. These sampled values do not rule out transients or spill. It did not open physical devices or execute an agent; the temporary synthetic WAV was removed on normal completion. Sample logs are under `.cache/asr-coding-20261116-230340-140.*`.

The existing binary's `--stream` option was also tested with `scripts/probe-crisp-stdin.py`: a synthetic French phrase was sent as 100 ms PCM blocks over stdin, with no WAV written by the probe. The runtime returned `fixture text`, emitted output before the input pipe closed, and reported a 3,000 ms step and 10,000 ms window. In this one run, first stdout arrived approximately 3,125 ms after process start; measured total was 3,328 ms for 98,560 bytes of 16 kHz PCM. The runtime warned that it ignored `--no-punctuation`. This shows a working piped path on synthetic input, not native incremental model support, word-level latency, a complete privacy audit, an agent integration or real-time quality. The process was not run under the comparison's resource watchdog. No network isolation was independently verified.

The partial preservation of `fixture` makes the CPU candidate worth further evaluation as an optional second opinion, but it does not justify replacing Vosk or silently normalizing filenames. A useful next test needs multiple real consented voices and filename examples, end-of-utterance latency and memory measurements, and explicit user review of disagreements before any agent task.
