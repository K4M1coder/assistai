# LFM3-Omni-2B candidate — 2026-11-17

## Hypothesis and primary sources

A compact native multimodal voice model might reduce duplication between the conversational audio and image paths while retaining a separate capable coding agent. [Liquid AI's model card](https://huggingface.co/LiquidAI/LFM3-Omni-2B) describes a 2.17B-parameter model accepting audio and images and generating text or speech; it lists French among supported speech languages and documents tool calls from spoken requests. The model card's multilingual ASR score aggregates several languages and its tool-call figure is an internal evaluation; neither establishes French conversational quality or tool reliability here. Its speech chat example is not evidence of simultaneous listening and speaking, and the card does not claim full duplex. The small model is not a replacement for the required capable coding agent without a separate evaluation.

The [publisher's GGUF card](https://huggingface.co/LiquidAI/LFM3-Omni-2B-GGUF) describes Q4 inference, Windows installation, and real-time speech with tool calls through llama.cpp's WebSocket API from b11960 onward. This is an upstream compatibility claim, not a result on this machine or a hard latency guarantee. The model uses the LFM Open License v1.0; review its actual terms before distribution. An LFM3-Audio sibling explicitly limits voice chat to English despite listing French speech recognition and synthesis; the Omni card lists French speech but does not establish French real-time conversation quality. Neither model card establishes robust speaker echo rejection or free barge-in.

## Local evidence and resource preflight

The existing local `LFM3-Omni-2B-Q4_K_M.gguf` is 1,099,630,080 bytes and the F16 projector is 949,841,248 bytes. Their SHA-256 hashes, respectively `9f8d30e9d4fd7a9349d586e077988229b3ca0a0e4ad730897563d1eccc9893e2` and `361bc95192c7d9156b566fcd4e48930363b78218e493fb1be607456bd51586e3`, match the publisher's file metadata at repository revision `d508b88f08a5b4286f2d2805a6a8d69a0ff44c72`. File sizes do not include KV cache, working memory, backend allocations or the separate agent. The publisher also offers a Q8 projector of 506,842,528 bytes, but it was not present or tested locally. No weights were downloaded.

The existing LM Studio Vulkan executable identifies itself as `0.9.0-dev`, commit `6c01da6`. Its version string alone does not establish ancestry from the upstream b11960 release or compatible realtime support. `scripts/run-lfm3-omni-idle-trial.ps1 -PreflightOnly` reported 11,684,564,992 bytes dedicated GPU, 149,266,432 bytes shared GPU and 15,499,886,592 bytes available RAM. It refused to launch because shared usage exceeded the deliberately conservative 128 MiB trial preflight threshold. The threshold preserves headroom below the existing 256 MiB sampled stop signal; it is a provisional planning rule, not a hardware guarantee. The current services and user connections were not disturbed.

The trial script parses successfully and can start only its own temporary server after preflight, sample adapter memory and RAM, and terminate that process on a threshold breach, telemetry failure or timeout. It tests model loading and health only, does not issue speech, image or tool requests, and has not been run beyond preflight. Sampling can miss spikes; neither the watchdog nor the server can prove no shared-memory allocation, disk paging or a strict 24 GB ceiling. The script requires the existing model files and local Windows Vulkan runtime; it is not a general installer.

## Follow-up: allocation investigation and controlled comparison

A later preflight observed 178,561,024 bytes shared and again rejected the load. A separate WDDM per-process sample attributed approximately 33.5 MB to `csrss`, 23.0 MB to the loaded Gemma server, 21.8 MB to VS Code, 19.3 MB to Edge, 16.9 MB to ChatGPT, 16.6 MB to ApplicationFrameHost, and 14.5 MB to the loaded text controller. These snapshots are approximate process accounting, not proof of which model tensors reside in shared memory. The user interface and system processes were not stopped. A subsequent preflight observed 215,982,080 shared bytes and also refused the trial.

The installed engine's help describes `--no-host` as bypassing a host buffer, not as a no-spill guarantee. It also exposes `--fit-device-limit` and `--fit-unified-limit` as *projected* allocation limits; no behavior or enforcement has been measured here. The existing server trial requests Q8 K/V caches and Flash Attention, but the help text does not prove those settings are supported or used by this model on the B60. The trial now offers `-DisableHostVisibleVidmem` for a controlled later A/B test of `GGML_VK_DISABLE_HOST_VISIBLE_VIDMEM`. The [upstream issue report](https://github.com/ggml-org/llama.cpp/issues/30888) describes a possible effect on different AMD hardware; it is not a B60 result. The installed Vulkan DLL contains the variable name, which does not prove that it is honored or useful. Both trial variants retain the same preflight and stop thresholds. The script also restores the parent process's environment after launching and quotes model paths containing spaces. PowerShell parsing and preflight were tested; neither launch variant has run.

## Next discrimination experiment

When the conservative preflight passes without disturbing another session, run the guarded idle trial and inspect its server log and memory trace. Only after a successful load, test synthetic French audio and image input, generated speech and structured tool proposals in a disposable environment; compare against the already tested LFM3-Audio path. Then test physical speech, interruption and direct delegation to a disposable agent task, measuring end-to-end latency and concurrent dedicated/shared GPU and RAM. The operator subsequently removed the task approval gate. Do not infer full-duplex, agentic capability or no-spill compliance from a successful load.

## Quantized projector preparation

The [publisher's GGUF instructions](https://huggingface.co/LiquidAI/LFM3-Omni-2B-GGUF) show the Q8 projector in their speech-synthesis example, but do not establish quality, compatibility or memory use on this machine. `scripts/setup-lfm3-omni-q8-projector.py` downloaded the official Q8 projector from revision `d508b88f08a5b4286f2d2805a6a8d69a0ff44c72` into ignored `.cache/lfm3-omni-research`. Its 506,842,528 bytes and SHA-256 `8a25f9d1931244429de404fccacfb7fb933970a36aa5688d2f5069f29c6b27b1` matched the publisher's repository metadata. This is 442,998,720 bytes smaller on disk than the existing F16 projector; it is not a measurement of VRAM saved or a quality comparison. The setup script checks disk space, bounds download size and verifies the digest. Review the model's LFM Open License before redistribution.

The guarded idle trial now accepts `-Q8Projector`; the same preflight and stop thresholds apply. `./scripts/run-lfm3-omni-idle-trial.ps1 -PreflightOnly -Q8Projector` found dedicated GPU 12,194,840,576 bytes, shared GPU 272,482,304 and available RAM 13,728,526,336, and refused to launch because shared usage exceeded 128 MiB. No model was loaded by this step. The option's real load, audio, vision, tool calling, latency, quality and resource behavior are unverified; the active demo is unchanged. The setup helper and the Q8 trial both verify the projector's pinned SHA-256 before use; the separately installed main model and F16 projector still rely on the earlier recorded verification.

After adding trial-side verification, the real Q8 file passed the hash check and a new preflight still refused at 270,385,152 shared GPU bytes. A separate PowerShell test replaced `Get-FileHash` with a function returning an invalid hash; the script rejected it before launch. This tests the failure branch with a mock, not disk corruption or model loading.

## Installed engine protocol inspection

The publisher separately describes LM Studio engine 2.65.1 or newer for image input and [llama.cpp b11960 or newer](https://huggingface.co/LiquidAI/LFM3-Omni-2B-GGUF) for `/v1/realtime` speech and tool calls. Those claims do not establish that an LM Studio packaged engine has identical audio support. In the installed `llama.cpp-win-x86_64-vulkan-avx2-2.71.0` directory, byte inspection found `/v1/realtime` and `input_audio_buffer.append` strings in `llama-server-impl.dll` and `lfm3` in several libraries. Strings only show that text is present, not that a model, backend or event sequence works.

As a non-inference protocol check, a WebSocket client connected to `/v1/realtime` on the already-running controller at loopback port 18084, sent no messages, and closed normally with code 1000. A follow-up waited for the first server event: the upgrade was accepted but the server returned `invalid_request_error`, stating that the current model does not support realtime transcription. The reproducible `node scripts/probe-realtime-handshake.mjs` now waits for `session.created` and therefore exits nonzero for this text model. This corrects the earlier inference from handshake alone: it establishes endpoint presence, not an operational audio session. It does not determine LFM3-Omni support, tool calls or interruption because that candidate was not loaded. A fresh Q8 preflight again refused at 272,482,304 bytes shared GPU versus the 128 MiB threshold.

At the next checkpoint, no native voice model was listening on the local demonstration ports. The older owned gateway on port 18097 had no established TCP connections; its recorded PID, start time and command line matched the running process. Following the operator's request to stop old instances, `scripts/stop-windows-demo.ps1 -Port 18097` stopped that gateway and its recorded sampler. Its volatile in-memory history was discarded. The mockup on port 3000 and current gateway on 18131 still returned HTTP 200. The Q8 preflight after cleanup observed 12,192,309,248 dedicated GPU bytes, 283,820,032 shared and 13,966,970,880 available RAM; it still refused the native model load. This cleanup did not establish a reduction in shared GPU allocations or make the native trial possible.

## Native bridge instruction correction

Review of the current bridge found a stale system instruction telling the model that proposed tasks require approval, despite direct delegation having replaced that workflow. The instruction now tells the model to delegate substantive tasks directly, report acceptance or rejection, and not claim completion before a result. A simulated native-gateway integration test checks the instruction both initially and after a session reset; the bridge, gateway and realtime-session suites passed 17 tests. These use simulated model and harness responses. No native model was loaded and the change does not demonstrate real tool calling or full duplex. Existing processes must restart to load the updated bridge.
