# LFM3-Omni-2B candidate — 2026-11-17

## Hypothesis and primary sources

A compact native multimodal voice model might reduce duplication between the conversational audio and image paths while retaining a separate capable coding agent. [Liquid AI's model card](https://huggingface.co/LiquidAI/LFM3-Omni-2B) describes a 2.17B-parameter model accepting audio and images and generating text or speech; it lists French among supported speech languages and documents tool calls from spoken requests. The model card's multilingual ASR score aggregates several languages and its tool-call figure is an internal evaluation; neither establishes French conversational quality or tool reliability here. Its speech chat example is not evidence of simultaneous listening and speaking, and the card does not claim full duplex. The small model is not a replacement for the required capable coding agent without a separate evaluation.

The [publisher's GGUF card](https://huggingface.co/LiquidAI/LFM3-Omni-2B-GGUF) describes Q4 inference, Windows installation, and real-time speech with tool calls through llama.cpp's WebSocket API from b11960 onward. This is an upstream compatibility claim, not a result on this machine or a hard latency guarantee. The model uses the LFM Open License v1.0; review its actual terms before distribution. An LFM3-Audio sibling explicitly limits voice chat to English despite listing French speech recognition and synthesis; the Omni card lists French speech but does not establish French real-time conversation quality. Neither model card establishes robust speaker echo rejection or free barge-in.

## Local evidence and resource preflight

The existing local `LFM3-Omni-2B-Q4_K_M.gguf` is 1,099,630,080 bytes and the F16 projector is 949,841,248 bytes. Their SHA-256 hashes, respectively `9f8d30e9d4fd7a9349d586e077988229b3ca0a0e4ad730897563d1eccc9893e2` and `361bc95192c7d9156b566fcd4e48930363b78218e493fb1be607456bd51586e3`, match the publisher's file metadata at repository revision `d508b88f08a5b4286f2d2805a6a8d69a0ff44c72`. File sizes do not include KV cache, working memory, backend allocations or the separate agent. The publisher also offers a Q8 projector of 506,842,528 bytes, but it was not present or tested locally. No weights were downloaded.

The existing LM Studio Vulkan executable identifies itself as `0.9.0-dev`, commit `6c01da6`. Its version string alone does not establish ancestry from the upstream b11960 release or compatible realtime support. `scripts/run-lfm3-omni-idle-trial.ps1 -PreflightOnly` reported 11,684,564,992 bytes dedicated GPU, 149,266,432 bytes shared GPU and 15,499,886,592 bytes available RAM. It refused to launch because shared usage exceeded the deliberately conservative 128 MiB trial preflight threshold. The threshold preserves headroom below the existing 256 MiB sampled stop signal; it is a provisional planning rule, not a hardware guarantee. The current services and user connections were not disturbed.

The trial script parses successfully and can start only its own temporary server after preflight, sample adapter memory and RAM, and terminate that process on a threshold breach, telemetry failure or timeout. It tests model loading and health only, does not issue speech, image or tool requests, and has not been run beyond preflight. Sampling can miss spikes; neither the watchdog nor the server can prove no shared-memory allocation, disk paging or a strict 24 GB ceiling. The script requires the existing model files and local Windows Vulkan runtime; it is not a general installer.

The script also restores the parent process's environment after launching and quotes model paths containing spaces. PowerShell parsing and preflight were tested; neither launch variant has run.

## Native bridge instruction correction

Review of the current bridge found a stale system instruction telling the model that proposed tasks require approval, despite direct delegation having replaced that workflow. The instruction now tells the model to delegate substantive tasks directly, report acceptance or rejection, and not claim completion before a result. A simulated native-gateway integration test checks the instruction both initially and after a session reset; the bridge, gateway and realtime-session suites passed 17 tests. These use simulated model and harness responses. No native model was loaded and the change does not demonstrate real tool calling or full duplex. Existing processes must restart to load the updated bridge.

The realtime adapter previously failed an entire response containing multiple tool calls. It now accepts at most four calls with distinct IDs, validates all before emitting any, starts bridge handlers concurrently, and waits for all results before returning them in original order and requesting continuation. This follows the general result-then-continuation sequence described in the [llama.cpp server protocol](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md). Unit tests cover out-of-order completion, duplicate IDs and parallel bridge submission with simulated services. Existing task admission can reject individual calls, and its estimates are not hard resource limits. No actual model or OpenCode multi-call execution was performed; timeout and transport failure can still leave task status uncertain. The running cascade gateway is unaffected.

`node --test prototype/native-parallel-admission.integration.test.mjs` additionally starts a real gateway process against simulated realtime and OpenCode servers and a synthetic resource sample. Two calls are issued in one response; the configured shared reservation budget permits only one. The gateway creates one agent session and one prompt, returns one accepted and one rejected tool result in original order, and requests one continuation after both. Four runs passed. The test does not load models, run OpenCode, establish real concurrency or enforce GPU allocations. Its temporary gateway and servers are stopped after the test; generated test databases remain under ignored `.cache`.

For interruption, the native bridge previously buffered at most one second of new PCM while waiting for cancellation or session setup. Its bounded buffer is now three seconds (96,000 bytes) and explicitly rejects and discards longer pending input rather than forwarding a truncated utterance. A simulated-session test covers the boundary and overflow; this adds at most 64,000 bytes per buffered bridge compared with the previous limit, excluding runtime object overhead. It does not measure actual cancellation latency, prove that three seconds is sufficient, solve speaker echo, or validate real-room barge-in. The active cascade is unchanged and existing gateways need restarting to load this source change.

### Explicit interleaved output and delegation follow-up

The current [llama.cpp realtime documentation](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md#realtime-conversation) says that omitting `output_modalities` allows the model to choose its output mode, whereas `['text', 'audio']` requests interleaved output. The experimental bridge instructed the model to produce both but omitted that session setting on the initial turn. We hypothesized that explicitly configuring it could improve consistency while preserving tool use. Unit and simulated integration tests passed, but these tests do not establish real model behavior.

Two guarded Q8 `-ReasoningOff` synthetic fixture trials then used the actual model and the read-only harness with the setting forced. Only two non-seeded trials were performed; this is not sufficient to isolate the cause or measure rates, but it contradicts the assumption that this configuration is a safe improvement over the two earlier successful direct-delegation examples. The setting was reverted; the native bridge remains experimental. The probe now prints partial results on timeout and exits unsuccessfully instead of losing them.
