# Piper French voice with DirectML: exploratory candidate

## Hypothesis and sources

A small local French text-to-speech model with GPU execution might replace the optional CPU Pocket TTS notification service, reducing model residency in system RAM and avoiding generative summaries. This does not address the remaining CPU recognizer or prove that all system allocations can be kept in VRAM.

[ONNX Runtime's DirectML documentation](https://onnxruntime.ai/docs/execution-providers/DirectML-ExecutionProvider.html) says the provider supports DirectX 12 devices, including Intel graphics, and is in sustained engineering while Windows ML receives new feature development. The [Piper source](https://github.com/OHF-Voice/piper1-gpl/blob/main/src/piper/voice.py) selects CPU or CUDA by default, so DirectML requires explicitly constructing its ONNX session; GPU execution is not a documented default of that loader. The [pinned French SIWIS model card](https://huggingface.co/rhasspy/piper-voices/raw/0c9c5d340496a47205a799eb046aab69334a88e9/fr/fr_FR/siwis/medium/MODEL_CARD) states French, 22,050 Hz and a CC-BY 4.0 dataset. Model and code licenses must both be checked before redistribution; current Piper code is GPL-3.0. A French/English mixed proper noun may remain problematic and must be tested, not assumed intelligible.

## Local setup and first attempt

On 2026-11-19, a separate ignored `.cache/piper-directml-env` Python 3.11 environment was created and loaded `piper-tts` 1.8.0 and `onnxruntime-directml` 1.23.0. Installing Piper normally also installed a separate `onnxruntime` 1.32.0 distribution into the same environment; reinstalling the DirectML wheel restored the imported 1.23.0 binaries. `pip check` reported no broken requirements, but overlapping distribution metadata makes this exploratory environment unsuitable as a reproducible production installation. A clean setup should install Piper without its default ONNX Runtime dependency and explicitly install the DirectML runtime and remaining dependencies.

The isolated import reported `DmlExecutionProvider` and `CPUExecutionProvider` available; this is only provider availability, not proof of graph execution or placement. Windows listed one video controller, Intel Arc Pro B60. The pinned SIWIS model was downloaded to ignored cache from revision `0c9c5d340496a47205a799eb046aab69334a88e9`; the 63,201,294-byte ONNX file has SHA-256 `641d1ab097da2b81128c076810edb052b385decc8be3381814802a64a73baf99`. Neither model weights nor environment are committed.

`powershell -NoProfile -File scripts/run-piper-directml-probe.ps1` runs the experimental Python probe with device ID 0, memory patterns disabled, sequential execution and ONNX Runtime's CPU fallback disabled. It saves a fixed synthetic notification only if synthesis succeeds and the output file does not already exist. The watchdog checks the same conservative whole-system preflight and runtime thresholds used in the native trial. Python and PowerShell syntax checks passed. Three initial attempts were refused before process launch because preflight shared GPU usage exceeded 128 MiB; a separate contemporaneous sample measured 180,154,368 bytes. No DirectML graph was loaded, no audio was generated and no performance or VRAM placement is established. Preflight telemetry is sampled and not an enforcement guarantee.

## Next experiment

When the unmodified preflight passes, run the watchdog, inspect its stdout, stderr and samples, and verify whether disabling CPU fallback allows the graph to initialize. If it does, compare generated audio with independent recognition and the Pocket TTS fixture while measuring latency and whole-system memory; provider selection and disabled fallback still do not independently prove that all tensors or weights stay in dedicated VRAM. If the graph requires CPU nodes or fails, record the exact error and evaluate its operator placement rather than silently accepting fallback. Concurrent native speech and agent load and human listening remain separate tests.
