# Playback-reference echo cancellation

The user reports that with speaker playback and the browser's requested echo cancellation, the microphone threshold must be raised to 10.5%, yet the assistant still sometimes interrupts itself and responds to its own output. This observation does not isolate whether the browser's AEC is enabled, what render reference it uses, or its residual echo level. Speaker-safe mode gates the microphone while output plays and avoids this loop at the cost of spoken interruption.

[WebRTC audio processing](https://webrtc.googlesource.com/src/+/refs/heads/main/api/audio/audio_processing.h) describes a reverse render stream for the echo reference and capture processing. [webrtcaec3.js](https://github.com/ennuicastr/webrtcaec3.js) exposes an AEC3 WebAssembly build with explicit render analysis and capture processing. Accurate timing between render and capture, device and browser buffering, clock drift, and double-talk require testing. The package is BSD-3-Clause with additional dependency license terms described upstream.

## EXP-014: fixed synthetic echo

`node scripts/probe-aec3.mjs` uses the local synthetic French test WAV, resamples by repetition from 24 to 48 kHz, and processes 12 seconds of 10 ms frames in one Node process. The artificial microphone signal has a fixed 50 ms delayed, attenuated copy of the render signal. From 8 seconds onward a different offset of the same voice is added as simulated near-end speech. No microphone or speaker was used.

On this Windows host, package `@ennuicastr/webrtcaec3.js` 0.3.0 ran in 322 ms. In the 4–8 second echo-only segment, input/output energy ratio was 45.64 dB. In a 9–12 second double-talk segment, output energy relative to the constructed near-end signal was -3.25 dB. This second metric is not near-end retention or intelligibility: residual echo and changed phase both contribute. A fixed synthetic path does not represent real devices, reverberation, clipping, nonlinear speaker effects, clock drift, unexpected system audio, or browser scheduling. No actual interruption or end-to-end recognition was tested. No GPU model was loaded.

Before enabling this in the client: feed the actual rendered signal, not arrival-time TTS packets, into AEC; align it with microphone capture in a shared timing domain; buffer in 10 ms blocks; quantify latency and underruns; isolate processor state per session; handle unsupported rates and failure with an explicit fallback; and check CPU budget. Replay real-room, consented echo-only, near-end-only and double-talk recordings against bypass and browser AEC. Measure false interruptions, words lost during real barge-in, echo reduction, processing tail latency and ASR error. Do not interpret output energy as proof that the user's voice survived.

## Render/capture framing prototype

`prototype/client/echo-reference-worklet.js` pairs two inputs from the same Web Audio graph into timestamp-order 10 ms blocks, padding a disconnected input with silence. `node --test prototype/echo-reference-worklet.test.mjs` exercises variable graph block sizes and disconnected playback. This is only sample framing: it is not wired to the client or AEC, does not measure the physical device delay, and does not compensate for clock drift. A future integration must bound the worklet-to-worker queue and report overload rather than letting latency grow indefinitely.

The experimental `echo-canceller-worker.js` now runs AEC3 on paired 48 kHz blocks; `echo-bridge.js` limits outstanding blocks and fails explicitly on overload. Tests use the real WebAssembly module for ordered frames and verify failure on a sequence gap. The caller must wait for worker readiness before connecting the worklet so that frame zero is not lost. These pieces have not been connected to the live graph or exercised in a browser; real-room echo cancellation and interruption remain unverified. The browser must serve the local AEC JavaScript and WASM with the correct paths and MIME types before integration.

## Experimental client integration

An opt-in client path now creates a shared 48 kHz playback/capture graph, routes the assistant's scheduled playback into the AEC reference input, and sends microphone capture through the paired-frame worker before ASR. Browser echo cancellation is requested off in this mode to avoid stacking two opaque cancellers. This request may not be honored. The worker stops microphone input and enables speaker-safe mode if processing fails or the bounded queue overflows. A stateful 63-tap low-pass filter precedes 48-to-16 kHz decimation; unit tests check passband, a 12 kHz alias case and continuity across arbitrary chunks. It has not been benchmarked or tested on actual speech for distortion. Audio sources already playing when the microphone is started are not connected retroactively to the reference; start capture before playback.

Four automated unit tests pass for mode handling, frame alignment, worker ordering, and overload; the separate gateway on port 18086 serves the JS and WebAssembly files with expected MIME types. These checks do not demonstrate browser execution or real-room quality. A live microphone test has been requested; test the status, echo-only false interruptions, then genuine spoken interruptions, with speaker-safe disabled only for the latter tests. This is an experimental echo filter, not the unimplemented enrolled-speaker isolation feature.

An additional synthetic pipeline test combines the worklet framing, the real AEC3 WebAssembly worker, and the streaming decimator. On a fixed-delay two-tone simulated echo it checks output length and at least 10 dB attenuation after four seconds of adaptation. This guards against broken wiring and sample counts, not real speech intelligibility or browser/device timing. Worker initialization now times out instead of waiting indefinitely.

The user subsequently reported that the experimental playback-reference filter did not prevent the assistant from cutting itself off when its speech reached the microphone. This is a negative real-room observation; the user did not provide a quantitative echo measurement or confirm every runtime setting. Keep speaker-safe mode as the fallback and investigate actual render/capture alignment and double-talk before claiming success.
