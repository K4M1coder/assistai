# Playback-reference echo cancellation

The user reports that with speaker playback and the browser's requested echo cancellation, the microphone threshold must be raised to 10.5%, yet the assistant still sometimes interrupts itself and responds to its own output. This observation does not isolate whether the browser's AEC is enabled, what render reference it uses, or its residual echo level. Speaker-safe mode gates the microphone while output plays and avoids this loop at the cost of spoken interruption.

[WebRTC audio processing](https://webrtc.googlesource.com/src/+/refs/heads/main/api/audio/audio_processing.h) describes a reverse render stream for the echo reference and capture processing. [webrtcaec3.js](https://github.com/ennuicastr/webrtcaec3.js) exposes an AEC3 WebAssembly build with explicit render analysis and capture processing. Accurate timing between render and capture, device and browser buffering, clock drift, and double-talk require testing. The package is BSD-3-Clause with additional dependency license terms described upstream.

## EXP-014: fixed synthetic echo

`node scripts/probe-aec3.mjs` uses the local synthetic French test WAV, resamples by repetition from 24 to 48 kHz, and processes 12 seconds of 10 ms frames in one Node process. The artificial microphone signal has a fixed 50 ms delayed, attenuated copy of the render signal. From 8 seconds onward a different offset of the same voice is added as simulated near-end speech. No microphone or speaker was used.

On this Windows host, package `@ennuicastr/webrtcaec3.js` 0.3.0 ran in 322 ms. In the 4–8 second echo-only segment, input/output energy ratio was 45.64 dB. In a 9–12 second double-talk segment, output energy relative to the constructed near-end signal was -3.25 dB. This second metric is not near-end retention or intelligibility: residual echo and changed phase both contribute. A fixed synthetic path does not represent real devices, reverberation, clipping, nonlinear speaker effects, clock drift, unexpected system audio, or browser scheduling. No actual interruption or end-to-end recognition was tested. No GPU model was loaded.

Before enabling this in the client: feed the actual rendered signal, not arrival-time TTS packets, into AEC; align it with microphone capture in a shared timing domain; buffer in 10 ms blocks; quantify latency and underruns; isolate processor state per session; handle unsupported rates and failure with an explicit fallback; and check CPU budget. Replay real-room, consented echo-only, near-end-only and double-talk recordings against bypass and browser AEC. Measure false interruptions, words lost during real barge-in, echo reduction, processing tail latency and ASR error. Do not interpret output energy as proof that the user's voice survived.

## Render/capture framing prototype

`prototype/client/echo-reference-worklet.js` pairs two inputs from the same Web Audio graph into timestamp-order 10 ms blocks, padding a disconnected input with silence. `node --test prototype/echo-reference-worklet.test.mjs` exercises variable graph block sizes and disconnected playback. This is only sample framing: it is not wired to the client or AEC, does not measure the physical device delay, and does not compensate for clock drift. A future integration must bound the worklet-to-worker queue and report overload rather than letting latency grow indefinitely.

The experimental `echo-canceller-worker.js` now runs AEC3 on paired 48 kHz blocks; `echo-bridge.js` limits outstanding blocks and fails explicitly on overload. Tests use the real WebAssembly module for ordered frames and verify failure on a sequence gap. The caller must wait for worker readiness before connecting the worklet so that frame zero is not lost. These pieces have not been connected to the live graph or exercised in a browser; real-room echo cancellation and interruption remain unverified. The browser must serve the local AEC JavaScript and WASM with the correct paths and MIME types before integration.

## Experimental client integration

An opt-in client path now creates a shared 48 kHz playback/capture graph, routes the assistant's scheduled playback into the AEC reference input, and sends microphone capture through the paired-frame worker before ASR. Browser echo cancellation is requested off in this mode to avoid stacking two opaque cancellers. This request may not be honored. The worker stops microphone input and enables speaker-safe mode if processing fails or the bounded queue overflows. A stateful 63-tap low-pass filter precedes 48-to-16 kHz decimation; unit tests check passband, a 12 kHz alias case and continuity across arbitrary chunks. It has not been benchmarked or tested on actual speech for distortion. Audio sources already playing when the microphone is started are not connected retroactively to the reference; start capture before playback.

Four automated unit tests pass for mode handling, frame alignment, worker ordering, and overload; the separate gateway on port 18086 serves the JS and WebAssembly files with expected MIME types. These checks do not demonstrate browser execution or real-room quality. A live microphone test has been requested; test the status, echo-only false interruptions, then genuine spoken interruptions, with speaker-safe disabled only for the latter tests. This is an experimental echo filter, not the unimplemented enrolled-speaker isolation feature.

An additional synthetic pipeline test combines the worklet framing, the real AEC3 WebAssembly worker, and the streaming decimator. On a fixed-delay two-tone simulated echo it checks output length and at least 10 dB attenuation after four seconds of adaptation. This guards against broken wiring and sample counts, not real speech intelligibility or browser/device timing. Worker initialization now times out instead of waiting indefinitely.

The user subsequently reported that the experimental playback-reference filter did not prevent the assistant from cutting itself off when its speech reached the microphone. This is a negative real-room observation; the user did not provide a quantitative echo measurement or confirm every runtime setting. Keep speaker-safe mode as the fallback and investigate actual render/capture alignment and double-talk before claiming success.

## EXP-068: native AEC3 and timestamped audio-client comparator

Hypothesis: a native AEC3 binding is viable on this Windows machine and a timestamp-aware audio client may offer a better basis for aligning physical playback and capture than the current browser experiment. The two claims require separate tests: a synthetic DSP test cannot establish real device alignment or real-room barge-in.

The [Hugging Face speech-to-speech echo guide](https://github.com/huggingface/speech-to-speech/blob/ebc09bf286edbe8739a59575709070f056d31e29/docs/echo-cancellation.md) describes a packaged client using `pywebrtc-audio` AEC3, Windows WASAPI timestamps and separate audio processing, with matching input/output rates and no independent device-clock drift correction. Its [implementation](https://github.com/huggingface/speech-to-speech/blob/ebc09bf286edbe8739a59575709070f056d31e29/src/speech_to_speech/api/openai_realtime/echo_canceller.py) pairs render samples against capture timestamps, and its [audio client](https://github.com/huggingface/speech-to-speech/blob/ebc09bf286edbe8739a59575709070f056d31e29/src/speech_to_speech/api/openai_realtime/audio_client.py) reads PortAudio ADC/DAC times and maps device stream clocks to a monotonic clock. The project's [README](https://github.com/huggingface/speech-to-speech/blob/ebc09bf286edbe8739a59575709070f056d31e29/README.md) describes a cascade, not a native speech-to-speech model; Windows is not in its stated CI compatibility matrix. No physical audio devices were opened and no upstream client was run in this experiment.

On Windows with Python 3.11.14, `pywebrtc-audio` 0.2.0 was installed without dependencies into a separate ignored research directory. `scripts/probe-native-aec.py` reused the 12-second fixed 50 ms synthetic path and fixture from EXP-014 (SHA-256 `de7a02ac447c49526f3ee76336ab6268ee7af389881150042fbe75fe86a612c7`). In one sequential run, native AEC3 took 178.29 ms with automatic delay estimation and measured 57.68 dB echo-only energy reduction; with a 50 ms hint it took 179.32 ms and measured 57.58 dB. The existing WASM probe, run afterward, took 329 ms and measured 45.64 dB. Double-talk output-to-near energy was -4.01 dB, -3.93 dB and -3.25 dB respectively; it is not a measure of intelligibility or user-voice retention. The implementations, filtering and measurement overhead differ, so this is a feasibility comparison, not a general performance ranking.

Next compare timestamp alignment and cancellation using consented real device captures, separate echo-only, near-end-only and double-talk cases, interruption false positives and speech loss. The native client could avoid GPU use for AEC, but its CPU load under concurrent inference, Windows device behavior, memory usage, speaker performance and integration with this gateway are untested. The code and dependency were not enabled in the product.

## EXP-069: synthetic timestamp alignment and overlap

Hypothesis: the pinned timestamp-aligned native comparator can maintain its synthetic echo reduction across different callback sizes and buffering delays while preserving some near-end signal during overlap. This tests its alignment and DSP with constructed times, not WASAPI device timestamps or real-room performance.

`scripts/probe-timestamp-aec.py` imports the inspected `EchoCanceller` at upstream commit `ebc09bf286edbe8739a59575709070f056d31e29` and uses `pywebrtc-audio` 0.2.0 from the ignored local research directory. It checks the source revision and the EXP-014 speech fixture hash. Twelve-second synthetic cases combine an attenuated delayed copy of the local synthetic phrase with a shifted copy of that same phrase as near-end speech. The reference is timestamped 256 ms or 1,000 ms ahead of the synthetic callback, with an additional 20 ms acoustic delay; the smaller callback has alternating 2 ms timestamp jitter. This follows the comparator's own synthetic testing pattern but does not represent independent speakers, room impulse responses, clock drift or nonlinear devices.

At 16 and 24 kHz, with 1,024- and 8,192-sample callbacks, echo-only energy reductions ranged from 61.21 to 62.74 dB. For the overlap window, maximum normalized correlation to the constructed near signal within 10 ms ranged from 0.628 to 0.856, and output-to-near norm ratio from 0.530 to 0.807. Near-only correlation ranged from 0.934 to 0.979. Output still contains residual echo and processing artifacts; correlation and level do not prove speech intelligibility or absence of clipped words. The 8,192-sample callbacks themselves represent substantial buffering latency and are stress cases, not recommended realtime settings.

The result supports a real-device comparison, not product integration or a claim that echo has been solved. Reproduce after placing the pinned source under `.cache/hf-speech-research` and installing the pinned binding under `.cache/pywebrtc-audio-research`, then set `PYTHONPATH` to that directory and run the script with `.venv-voice` Python. Real speaker/microphone timing, interruptions, CPU load during inference and the end-user's voice remain untested.

## EXP-070: Windows format checks and streaming playback conversion

The candidate native AEC requires matching capture and render rates, while the current gateway accepts 16 kHz microphone PCM and emits 24 kHz speech. On this machine, PortAudio via `sounddevice` 0.5.3 reported default WASAPI input at 48 kHz and output at 44.1 kHz. Format checks with WASAPI shared-mode auto-conversion reported 16, 24 and 48 kHz mono PCM16 as supported for both default devices. These checks did not open streams, play sound or capture the microphone; they do not prove stable operation or actual end-to-end latency.

Added `prototype/native_pcm.py`, a stateful `soxr` 1.1.0 24-to-16 kHz PCM16 converter that handles odd-byte packet boundaries, flushes the final filter tail, and must be reset per response. Two unit tests check streamed output against a one-shot conversion, sample count, packet boundaries and truncated final input. With the EXP-014 synthetic speech fixture sent in 20 ms input chunks, the first output appeared after 40 ms of input and the largest emitted block represented 30.625 ms; 308 output samples were emitted on final flush. These are resampler buffering observations, not wall-clock or device latency. The converter is not connected to an audio client or gateway yet.

## EXP-071: native playback buffer against local gateway

The experimental native playback buffer now converts gateway output to 16 kHz, limits queued audio, zero-fills underruns and discards queued or late response data on interruption. Three unit tests cover interruption, stale response rejection, overflow and malformed final samples; two converter tests also pass. A device-free real-gateway probe sent a short text request, received 24 kHz speech, drained the converted queue in nominal 20 ms intervals and observed 71,040 output bytes including 32,565 nonzero PCM16 samples. The count includes zero-filled time; no audio was played or listened to. This verifies a gateway-to-buffer path, not a complete native client, physical timing, audible quality or end-to-end interruption.

## EXP-072: synthetic microphone turn and backpressure

Added an experimental 20 ms energy-based native turn detector with bounded pre-roll, a speaker-safe gate and an optional interruption event. Four unit tests cover onset, end, gating and event order; this is not speaker identification and does not establish noise robustness. `scripts/probe-native-turn.py` sends the synthetic French `reset-question.wav` through the detector into the real local cascade gateway and drains the native playback buffer without physical devices.

The first run overflowed the three-second playback queue because the server produced audio faster than the simulated playback consumer. The probe was changed to process response chunks in smaller pieces and pause receive-side consumption above two seconds of queued output. A repeat produced one start and one end, the correct synthetic question transcript, a model response and 128,216 nonzero output samples. This is a probe-level pacing strategy, not yet production flow control: the gateway and network layers may still buffer while the receiver waits, and no actual speaker or microphone was exercised. Nine PCM, buffer and detector unit tests passed. Live interruption, echo, bounded end-to-end memory and loaded CPU behavior remain unverified.

## EXP-073: experimental native Windows client with synthetic devices

`prototype/native_audio_client.py` connects the tested turn detector and 16 kHz playback buffer to a loopback gateway and default Windows WASAPI streams. It defaults to speaker-safe gating; experimental `--aec` loads the pinned external AEC comparator, enables voice interruption, aligns callbacks using ADC/DAC stream timestamps, and stops on audio or AEC errors rather than continuing with raw capture. Receive-side pacing bounds the application playback queue, but does not establish bounded buffering across the server and network. This is an opt-in research client, not evidence of stable physical-device operation.

With the real cascade gateway running, `scripts/probe-native-client-fake.py` replaced audio devices with synthetic callbacks and replayed the French question. Both the default and AEC-enabled runs observed the expected Vosk transcript, nonzero output samples and closed streams; no physical devices were opened. The AEC-enabled run exercised the real native AEC binding, but its synthetic input did not contain a physical speaker echo. Ten Python component tests passed, including rejection of non-loopback gateway URLs before audio access. Real WASAPI opening, live microphone, speaker echo, genuine barge-in, audible quality and multi-turn stability remain unverified.

## EXP-074: synthetic native-client playback loopback

Extended the synthetic-device test so microphone callbacks receive a copy of the preceding output callback after the test utterance, without opening any physical audio devices. This is a simple digital loopback with independent callback scheduling, not a measured room, realistic acoustic impulse response or double-talk. A `playback.interrupted` client event records the time since speech start.

With experimental native AEC and a 1% detector threshold, two runs each falsely interrupted playback; the instrumented run did so 3,593 ms after speech start. With the client's default 2.5% threshold, another run falsely interrupted after 1,765 ms. In a speaker-safe run at 1%, there was one user transcript and no playback interruption. These are separate stochastic model responses, not a controlled paired benchmark; they do not establish physical-device performance or recall of a real interruption. The result disproves treating native AEC as a reliable speaker solution, even though earlier fixed-path DSP tests showed strong echo-only attenuation. More realistic timestamp calibration, echo-path and double-talk tests are needed before enabling AEC by default.

## EXP-075: residual peaks and onset tradeoff

In a further synthetic native-client loopback at the default 2.5% threshold, the AEC path again falsely interrupted playback, 8,875 ms after speech start. A test-only wrapper measured 333 post-playback capture frames: the 95th-percentile raw RMS was 0.1748, cleaned RMS was 0.0100, and 10 cleaned frames exceeded the 0.025 threshold. The figures are aggregate synthetic callback measurements, not physical-room measurements or proof of which frames caused the interruption.

`scripts/probe-aec-onset.py` separately replayed the same deterministic 12-second synthetic fixture through the pinned timestamp-aligned comparator and the energy detector. An ideal fixed 20 ms echo path produced no interruptions in the echo-only case at onset requirements of 3, 5 or 10 consecutive 20 ms frames. With a shifted copy of the same synthetic voice added from 8 seconds, the first interruption occurred 60 ms after that constructed overlap began for 3 frames, 680 ms for 5 frames, and not at all within the remaining four seconds for 10 frames. Times include completion of the triggering frame; they are measured from the constructed overlap boundary, not from verified speech onset. This idealized replay does not reproduce callback jitter in EXP-074, and its two voices are not independent.

The hypothesis that simply increasing sustained onset fixes self-interruption without harming user interruption is not supported by this small controlled fixture. No production threshold was changed. Real acoustic captures, multiple voices, word loss, clock drift and end-to-end interruption tests remain necessary.

## EXP-076: manual native-client interruption

The Windows native client now accepts `I` in an interactive terminal to clear local playback and send a manual interruption event; `Q` ends the client. A unit test verifies that the keyboard handler clears playback, resets turn detection and sends the expected event. A separate synthetic-device test against the running local cascade injected `I` after 1,000 nonzero playback samples: it observed the user transcript, one manual interruption event, nonzero output and closed fake streams. The probe did not use physical devices or independently measure when a physical speaker stops; no claim is made about live keyboard behavior, operating-system buffering or actual microphone interruption.

## EXP-077: low-volume physical WASAPI probe

`scripts/probe-wasapi-aec-live.py` opened the default Windows WASAPI input and output at 16 kHz mono, played eight seconds of the existing synthetic speech at a peak digital amplitude of 0.08, and processed the microphone input using the pinned native AEC comparator. It retained only aggregate levels and threshold counts; no microphone audio was saved. Both streams opened and closed successfully in two runs. This was a standalone DSP probe, not the gateway client, and there was no controlled near-end speaker or verified echo-only recording. Ambient sounds or speech could contribute to capture levels, and no word intelligibility, true barge-in, actual acoustic delay or CPU load was measured.

During the measured 2–7 second window, the first run collected 250 20 ms frames: raw RMS 0.012093, cleaned RMS 0.010636, with 13 raw and 7 cleaned frames above 0.025. The second run collected 249 frames: raw RMS 0.012579, cleaned RMS 0.008235, with 15 raw and 3 cleaned frames above 0.025. The longest cleaned above-threshold streak in the second run was two frames; the current detector uses three consecutive frames, but the probe did not run the detector and excluded the first two seconds and final second. These total-level statistics are not an echo attenuation measurement or evidence that the speech model can be interrupted reliably. Playback volume, devices, room and other audio were not controlled.

## EXP-078: physical native-client smoke test

An isolated local cascade gateway and the default speaker-safe native client were used for a physical-device test with a low-volume 16 kHz synthetic French question and a 0.5% detection threshold. The first attempt tried to open a second playback stream and failed with a Windows audio-driver host error. A revised probe inserted the synthetic question into the client's existing output stream. It observed one transcript event, one assistant response and 245,999 nonzero playback samples, but did not recognize the expected question; the intended end-to-end check failed. The room and other sound sources were uncontrolled. Neither transcript nor response text was printed by the probe, and no microphone audio was saved. The synthetic question and assistant output were physically played; audible quality and whether other audio caused the transcript are unknown.

The isolated gateway was stopped. Its temporary SQLite transcript database at `.cache/physical-native-probe-20261111/events.sqlite` remains because the execution environment blocked the requested deletion; it may contain a local transcript and must not be committed. This run did not exercise AEC, actual user voice or live interruption.

## EXP-079: volatile gateway history for isolated probes

The gateway now recognizes `ASSISTAI_DB_PATH=:memory:` as SQLite's process-local in-memory database rather than resolving it as a filesystem path. Its `/health` response reports whether gateway history is `volatile` or `file`. The physical client probe now validates a loopback URL and requires a `volatile` health response before opening audio devices. This is a convenience check against accidental use of the file-backed demo, not authentication, secure erasure, or proof that operating-system paging or other components never write related data to disk.

An isolated in-memory gateway passed a device-free real cascade playback probe, returning 81,280 output bytes including 37,763 nonzero samples; the gateway was then stopped. A separate check against the file-backed demonstration failed before opening audio devices, as intended. A mock gateway test checked startup and the health response. No physical microphone test was repeated, and EXP-078's earlier file remains because its deletion was blocked.

## EXP-080: physical synthetic-question threshold comparison

Two further standalone physical native-client runs used an isolated gateway with `ASSISTAI_DB_PATH=:memory:` and no configured agent. The client ran in speaker-safe mode and injected the existing 16 kHz synthetic question into its own WASAPI output stream at 0.08 peak digital amplitude. The probe retained only aggregate frame levels and result counts, not microphone audio or transcript text; SQLite history was process-local and the test gateway was stopped after each run. This does not rule out operating-system paging or retention by other components. The room and system volume were uncontrolled, so captured sound may include other sources.

At a 0.5% detector threshold, the one-second pre-injection capture averaged 0.008794 RMS; 34 of 50 frames were above 0.005. During injection, RMS was 0.015050. One transcript and one response were produced, but the expected question was not recognized; playback contained 226,691 nonzero samples. A different run at 2% recorded pre-injection RMS 0.008768, with no pre-injection frames above 0.02. During injection, RMS was 0.013913, with 15 of 81 frames above threshold and a maximum consecutive run of 10 frames. It again produced a transcript and response but not the expected question, with 128,033 nonzero playback samples. The after-injection measurement includes possible output playback and background sound; it is not an echo-only metric.

The low-threshold run was vulnerable to background triggering; the higher-threshold run demonstrates threshold crossings but not that they originated from the synthetic question. Neither run confirms the output's audible content or intelligibility. This small uncontrolled experiment cannot isolate the cause of failed recognition, establish a generally suitable threshold or assess a real person speaking. No physical AEC or voice interruption was tested.
