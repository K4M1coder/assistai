# EXP-195: Preserve uncertain agent status in conversation context

Hypothesis: omitting a monitoring failure from session context can cause the voice controller to reason from an older `task.started` event even though the actual task status is unknown. The risk is especially relevant because OpenCode's [server API](https://github.com/anomalyco/opencode/blob/dev/packages/web/src/content/docs/server.mdx) documents `prompt_async` as returning HTTP 204 without waiting for completion; that response is not evidence of a successful task. Upstream [issue 12738](https://github.com/anomalyco/opencode/issues/12738) describes one historical async failure with no assistant response, and [issue 45610](https://github.com/anomalyco/opencode/issues/45610) describes stuck status in a development version. These reports concern their stated versions and circumstances, not proof of those bugs on this machine.

The previous gateway stored `task.uncertain` but omitted it from task summaries, agent and native context, and resumed task history. It also sent monitoring recovery without recording it. The gateway now includes uncertainty in those contexts, records recovery, and explicitly states that the task outcome remains unconfirmed. The browser displays both historical events without treating them as current proof of execution. No status event itself establishes that the requested work succeeded. Context is bounded and can still omit older events; the controller may still misunderstand or hallucinate.

A mock-backed gateway integration exercises failed polling followed by recovery, verifies both events in SQLite and retains the task resource reservation until confirmed completion. Context tests verify uncertainty and recovery, including a submission failure payload that also contains a task. These checks used local mock services, not a real provider failure or physical conversation. Running gateway processes need a restart to load the backend change; existing sessions were preserved.
