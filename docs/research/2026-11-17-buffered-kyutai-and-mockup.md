# Buffered Kyutai input and mockup memory — 2026-11-17

## Hypothesis and same-audio comparison

The previous end-to-end arithmetic question failed because Vosk changed `deux plus trois`. The already downloaded Kyutai Q4 candidate may recover this utterance, though its file-mode CPU path adds latency and is not a verified streaming implementation. `scripts/run-asr-coding-probe.ps1 -CompareCrisp -Kyutai -VoiceCases -ComparePadding` synthesized each fixed French phrase once and sent the same PCM to Vosk and to Kyutai with and without one second of appended silence. For the arithmetic phrase Vosk returned `combien font de plus trois répond en mot`, while both Kyutai variants returned `combien font deux plus trois réponds en un mot` (normalized WER 0.333 and 0.000 respectively). Both retained the main terms for the capital question. This is one synthetic voice and two sentences, not evidence of broad superiority or noisy-room performance. Vosk's timing included paced transmission; Kyutai's included model loading, so they are not comparable streaming latencies.

The 22 whole-system samples reported peak dedicated GPU 12,203,315,200 bytes, peak shared GPU 227,328,000 bytes and minimum available RAM 9,702,801,408 bytes. Sampling does not establish hard limits or rule out paging. Synthetic logs are under `.cache/asr-coding-20261117-193549-500.*`.

## Experimental local sidecar and file loopback

`prototype/kyutai_asr_server.py` implements the gateway's ASR WebSocket protocol as an experimental *utterance-buffered*, CPU-only service. It keeps at most 30 seconds of PCM, runs the pinned CrispASR binary with the verified Q4 model and one second of trailing silence, and returns a final transcript. It does not produce incremental partials; it reloads the model each utterance and is not native real-time full duplex. It requires a fresh Windows resource sample in `ASSISTAI_KYUTAI_BUDGET_PATH`, rejects or terminates its own subprocess on stale telemetry, pressure or timeout, and serializes transcription jobs. The preflight requires 8 GiB available RAM and the running stop threshold is 6 GiB; a later addition of the 8 GiB preflight is covered by simulated tests and was not present for the two earlier successful runs. The threshold check is sampled and cannot guarantee no spill or prevent all transients. It writes a temporary WAV under `.cache` and removes it on normal completion; a crash or forced termination can leave audio there. Cancellation during a running transcription and concurrent users need further work.

For research only, with the existing port 18131 resource sampler running, the sidecar was started on loopback port 18132 with `ASSISTAI_KYUTAI_BUDGET_PATH` pointing to `.cache/assistant/demo-18131-resource.json`. `scripts/run-asr-coding-probe.ps1 -VoiceLoopback -KyutaiInput -VoiceScenario math` sent a synthetic WAV through a separate temporary gateway with no agent configured, then used the existing Vosk service to transcribe the generated output audio. In the first trial, Kyutai returned `combien font deux plus trois répond en un mot`, the local controller answered `Deux plus trois fait cinq. Réponse : **5**.`, and Vosk's output transcription included `cinq` but had WER 0.571 against the text. In the repeat, Kyutai returned `combien font deux plus trois réponds en un mot`, the controller answered `Deux plus trois fait cinq. La réponse est **cinq**.`, and Vosk transcribed `de plus trois fait cinq la réponse est cinq` (WER 0.111). The expected answer token appeared in both text and output transcription; neither an automated ASR match nor this token check proves human intelligibility or semantic correctness for arbitrary responses.

For the timed repeat, 2,920 ms of synthetic input took 3,266 ms to send; transcript arrived 3,281 ms after input ended and the first output audio 3,750 ms after input ended. This does not satisfy a low-latency real-time target and is not a physical-microphone or interruption test. The first run had 14 whole-system samples, peak dedicated 12,154,437,632 bytes, peak shared 237,682,688 bytes and minimum available RAM 8,081,842,176 bytes. The repeat had 13 samples, peak dedicated 12,122,673,152 bytes, peak shared 240,435,200 bytes and minimum RAM 8,323,145,728 bytes. These exclude unobserved transients and cannot prove no GPU spill or paging. Logs are `.cache/asr-coding-20261117-194019-272.*` and `-194113-055.*`. The main gateway still uses Vosk; the sidecar is not a default replacement.

The Windows launcher now accepts `-KyutaiASR` to select a separately running healthy sidecar for a new gateway and reports its buffered mode in service discovery. This configuration has not been launched end to end after the launcher change; the main demonstration was not restarted. The experimental sidecar was stopped after testing because no gateway used it and the available RAM had fallen close to the running reserve.

On 2026-11-18, review found that cancelling a client coroutine while `asyncio.to_thread` was running could release the async lock even though Python cannot stop the underlying thread. The sidecar now retains the lock in a shielded task until the transcription thread completes; a cancelled request still waiting for the lock is discarded. A simulated async concurrency test checks both cases. A second test uses real Python worker threads with a deliberately blocked substitute transcription function, and confirms that a subsequent call waits after the first client is cancelled. Neither test starts a model subprocess or applies actual memory pressure: a running transcription still completes subject to its existing watchdog, and a disconnect is not necessarily observed during the inference wait. No live sidecar was restarted for this change.

The sidecar now admits at most two completed utterances to transcription: one executing and one waiting. Further submissions receive the existing generic ASR error and empty final transcript. A simulated concurrent test verifies rejection and release of capacity. This is a per-process limit, not an OS memory limit: multiple server processes or arbitrarily many connected sockets buffering their individual utterances can still consume memory. It has not been exercised against a live model or multiple real browser clients.

## Mockup memory observation

The existing Vite development server's process was observed at 1,423,556,608 bytes working set and 2,055,741,440 bytes private memory. Its log showed reloads triggered by generated `.cache` files. With no connected clients, it was stopped and the same built mockup was served in production/static mode on port 3000; the replacement process initially reported 85,184,512 bytes working set and 46,567,424 bytes private memory, returned HTTP 200, and headless Chrome rendered a populated React root. Different process lifetimes and workloads make this a practical snapshot, not a controlled benchmark or total system-memory accounting. No model server was stopped.

`npm run build` followed by `npm run start:mockup` reproduces the static mode; it requires an existing build and does not run Vite's development watcher. The dev configuration now ignores generated caches in its watcher, as supported by [Vite's server options](https://vite.dev/config/server-options#server-watch); its impact on sustained memory has not been measured. The mockup remains separate from the voice gateway and contains simulated functionality.
