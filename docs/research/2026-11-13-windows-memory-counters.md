# EXP-173: Windows memory-counter interpretation

With the agent model idle, Windows reported 13,822,300,160 bytes private commit, 10,805,248 bytes current working set and a 4,275,286,016-byte peak working set for the agent process. The system pagefile reported 4,608 MiB current usage. This is one snapshot; counters and the workloads on the machine change over time. The running process uses `--load-mode none --no-host --cache-ram 0`, but those flags do not themselves prove that all model data remains resident in dedicated GPU memory.

[Microsoft's process memory documentation](https://learn.microsoft.com/en-us/windows/win32/api/psapi/ns-psapi-process_memory_counters_ex2) defines private usage as committed private memory; the [working-set definition](https://learn.microsoft.com/en-us/windows/win32/memory/working-set) describes pageable pages currently resident in physical memory. The [pagefile counter](https://learn.microsoft.com/en-us/windows/win32/cimwin32prov/win32-pagefileusage) reports system pagefile use, not per-model attribution. These figures do not establish how much of the model or which process accounts for the used pagefile. A sample alone cannot prove no SSD access, identify all GPU allocation types, or establish residency over time.

The Windows sampler can now include optional system-wide pagefile usage. Resource status also warns when total shared GPU use exceeds 256 MiB, even when task admission is disabled. Pagefile use is presented as system-wide information, not a per-process measure or an automatic admission decision. Unit tests cover optional, missing and invalid data and the shared threshold; PowerShell parsing passed. Existing running sampler and gateway processes must be restarted to expose the new field, and old samples remain compatible.
