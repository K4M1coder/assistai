# Experimental local voice components

These components are an early implementation, not the complete assistant. The React web UI is a separate mockup. The gateway serves its own experimental browser client, which has been exercised interactively; live interruption and echo handling remain incomplete.

Current gateway source requires explicit approval of every proposed agent task. The browser presents the original request and proposed task; inspect identifiers, direction, negation and scope before choosing Approve or Decline. A pending proposal expires after five minutes and is discarded on disconnect. The native terminal client prints the proposal and accepts `Y` or `N`; native speech may not provide the original request for comparison. Approval is not an OS sandbox, and previously started gateway processes do not acquire this safeguard until restarted. See [EXP-186](../docs/research/2026-11-14-task-approval.md).

## French speech recognition

`native_pcm.py`, `native_playback.py` and `native_turn.py` provide experimental PCM conversion, buffering and energy-based turn handling. `native_audio_client.py` connects them to default Windows WASAPI input and output. In one user-reported test it understood a spoken French question and manual interruption worked; an earlier physical smoke test did not recognize its synthetic question. It opens the microphone and speaker when run. Speaker-safe is the default; in an interactive terminal press `I` to interrupt playback, or `Q` to quit. `--aec` opts into the pinned, separately installed AEC comparator and enables voice barge-in. AEC mode interrupted its own playback in synthetic loopback tests and is not ready for reliable speaker use. A separate idealized replay showed that longer onset detection can miss near speech. Only loopback gateway URLs are accepted. AEC failure stops the client rather than passing raw microphone audio.

The native client queues up to 20 completed-task notifications and requests speech when it is not capturing a turn, awaiting a response or playing audio. A rejected request is retried at two-second intervals up to three attempts; a manually interrupted notification is not replayed. The oldest pending notification is discarded if the queue fills. Task results still appear in the terminal. A mock-gateway, fake-device test is `node scripts/probe-native-client-notification.mjs`; real-device timing and spoken accuracy remain unverified.

For research, `--speaker-enrollment path/to/voice.wav` enables CPU target-speaker extraction with an explicit 3–30 second mono 16 kHz PCM16 WAV, after installing the VoxLock experiment dependencies and models described in the noisy-room research notes. It cannot be combined with `--aec`; speaker-safe playback and manual interruption remain in effect. The client reads but does not delete the enrollment file. This option is unvalidated with physical voices and may clip speech or select an unintended speaker; it is not authentication. An immediate-onset synthetic-device test lost most of the question before a 200 ms internal silence warm-up was added; one test afterward transcribed it correctly. Do not infer robust noise suppression or automatic voice interruption from this experiment.

To record an enrollment sample explicitly on Windows, first install `python -m pip install -r prototype/requirements-native-audio.txt` into the voice environment and set up VoxLock as described in the noisy-room research notes. Choose a quiet room and run the following from the repository root. Recording starts when the command says so; speak naturally for the requested duration. The file contains your voice and persists until you delete it yourself. Choose a different new path if it already exists. The command will not overwrite an existing file and does not check that the sample contains the intended speaker.

```powershell
.\.venv-voice\Scripts\python.exe -m prototype.enroll_speaker .cache/my-speaker-enrollment.wav --seconds 8
.\.venv-voice\Scripts\python.exe -m prototype.native_audio_client --speaker-enrollment .cache/my-speaker-enrollment.wav
```

The enrollment command accesses the default microphone only when run, buffers the recording in memory and writes the WAV after capture. A capture overflow aborts before writing; an interruption or disk error during writing may leave a partial file. The chosen gateway and other services have their own storage behavior.

On this research machine, with the cascade gateway running, the optional dependencies already reside in `.cache/pywebrtc-audio-research`. Run from the repository root in PowerShell:

```powershell
$env:PYTHONPATH="$((Get-Location).Path);$((Resolve-Path .cache/pywebrtc-audio-research).Path)"
.\.venv-voice\Scripts\python.exe -m prototype.native_audio_client
# Experimental AEC and voice interruption: append --aec
```

Session events then live in a process-local SQLite database until the gateway exits; `/health` reports `history_storage: volatile`. For optional Windows resource reporting, run `scripts/write-windows-budget-sample.ps1` with the correct adapter identifier and a local output file, then set `ASSISTAI_RESOURCE_STATUS_PATH` to that file before starting the gateway. `/resources` and the browser show fresh dedicated/shared GPU usage, available RAM, low-reserve conditions and whether separate task admission is enabled. Missing or older-than-five-second samples are not presented as current. Reporting neither reserves memory nor blocks tasks; it does not identify model offload or enforce a hard VRAM limit. If `ASSISTAI_BUDGET_SAMPLE_PATH` is configured, the same sample can also be used for the separately configured advisory task-admission policy.

When both use the same configured sample path, `/resources` additionally projects the configured estimate for one task using the admission budget. It excludes active task estimates and is only a snapshot, so a positive projection does not guarantee admission. The projection is omitted when the reporting and admission sample paths differ. Restart the gateway to load this endpoint change.

The cascade reports empty or incomplete PCM16 speech as an error. The browser clears playback when an error identifies the current speech turn, so a failed stream does not leave playback marked active. This does not detect every truncated or unintelligible response.

After a gateway disconnect, the browser retries with a capped delay. It pauses audio transmission while disconnected, resets an interrupted push-to-talk press and retains unsent text. An already enabled microphone stays enabled and resumes sending after recognition becomes ready. Without opt-in session resume, reconnect starts a new session; a policy rejection requires intervention. A lost cascade ASR connection closes the gateway connection so it can be re-established. This behavior has mock and simulated-DOM tests, not a physical microphone or browser reconnect test.

Create a Python 3.11 or 3.12 environment, install the pinned direct dependencies in `requirements.txt`, then run `python scripts/setup-vosk-fr.py` from the repository root. Set `ASSISTAI_VOSK_MODEL` to use a different Vosk model directory.

From the repository root, start `python -m uvicorn prototype.asr_server:app --host 127.0.0.1 --port 18082`. `GET /health` reports readiness. The `/asr` WebSocket accepts binary mono 16 kHz little-endian PCM16 frames of at most one second. It emits JSON `partial` and `segment` events while audio arrives. Send `{"type":"end"}` to receive a `final` event and reset the recognizer, or `{"type":"reset"}` to discard the current utterance. Clients must collect `segment` events as well as the final text for longer utterances.

## Limitations

The experimental browser client has been exercised with a live microphone, but sustained performance, accurate interruption and noisy-room behavior remain unverified. There is no authentication or enforced resource policy yet. Bind the sidecar to loopback and avoid exposing it to the network. Vosk's small French model is a baseline, not the final model choice; compare it against Kyutai STT and other candidates with an authorized corpus.

The browser retains a spoken task notification until its queued audio sources have finished and requeues it when interrupted. This includes the interval after the server has finished sending audio. The behavior is covered by a simulated browser test; physical playback and recovery across a dropped connection are not verified, and the pending queue is cleared on disconnect.

After reconnecting to a resumed session, **Replay latest task result** can explicitly request an announcement for the most recent completed task present in the bounded history. The request uses the same session-scoped result lookup as live notifications; no automatic replay is performed. Browser simulation and mock gateway tests cover the flow, but audible playback remains unverified.

`gateway.mjs` is a separate experimental integration of the sidecar, a local OpenAI-compatible model server, and a local Pocket TTS server. It serves an experimental browser client at `http://127.0.0.1:18083/`, accepts text or PCM through `/voice`, and writes conversation events to `.cache/assistant/events.sqlite`. Optionally, `ASSISTAI_OPENCODE_URL` enables background delegation to a separately configured OpenCode server. Task completion is emitted as an event; the experimental browser queues a spoken notification when idle. OpenCode's own permissions apply: the gateway is **not** a sandbox. It must not be exposed to the network. Its short synthetic-audio test is `scripts/test-voice-gateway.py`; `scripts/test-gateway-delegation.mjs` exercises a read-only fixture. Neither test establishes live microphone performance or sustained hardware-budget compliance.

When the cascade gateway advertises `spoken_image_input`, an image selected and loaded in the browser is attached to the next completed spoken question. It is cleared after sending; if no speech is recognized, select it again. An older gateway or native speech mode does not accept this feature. One synthetic French question and generated red image succeeded through the real local services; physical microphone, browser file selection and general image understanding remain unverified. Before TTS, common Markdown, HTML, code blocks, URLs and emoji are converted or removed by a heuristic; speech may omit details. See EXP-138 and EXP-143.

For diagnosing choppy playback, the client logs the number and longest duration of gaps over 30 ms between scheduled chunks within a speech stream. This uses the browser audio clock and is not a measurement of microphone input, pronunciation or actual device output. It has mock-clock coverage; browser and device behavior still need validation. See EXP-139.

The browser now preserves adjacent chunk scheduling while audio is queued, adding a 40 ms lead only at stream start or after an underrun. `scripts/run-tts-pacing.ps1` measures synthetic local TTS delivery against an approximate virtual queue with sampled B60 resource guards. It does not open audio devices, measure browser behavior or assess intelligibility. See EXP-140.

The cascade removes explicit `<think>` and `<analysis>` blocks from model answers before display, event history and TTS; notification speech also removes such sections from task results. A malformed opening block is dropped through the end, potentially omitting the answer. Other or unmarked reasoning formats may still appear. Direct native-model speech is not covered. The mock gateway test checks the text presented to the user and sent to TTS; live behavior requires a restarted gateway and user verification. See EXP-141.

The client defaults to **speaker-safe mode**: it pauses microphone input while generated speech is playing to prevent acoustic feedback. Use the Interrupt button to stop the assistant and reopen the microphone. Uncheck the setting to experiment with automatic spoken interruptions; echo and false interruptions are not yet solved in that mode.

On Windows, `scripts/measure-windows-memory.ps1 -ModelPid <pid>` samples dedicated and shared GPU allocations, model process memory, available physical RAM and global page-file use. Establish a baseline before starting services and compare it with sustained audio, vision and agent workloads. This is monitoring, not an automatic memory limiter.

`resource-budget.mjs` contains an admission policy for dedicated GPU memory, shared-memory growth and system RAM reserves. An optional gateway check applies it before launching a background task. To enable it, provide `ASSISTAI_BUDGET_SAMPLE_PATH`, `ASSISTAI_BUDGET_BASELINE_SHARED_BYTES` (measured before model loading), and positive `ASSISTAI_TASK_VRAM_ESTIMATE_BYTES` and `ASSISTAI_TASK_RAM_ESTIMATE_BYTES`. `scripts/write-windows-budget-sample.ps1` can continuously publish snapshots for an explicitly selected Windows adapter. Missing, malformed or older-than-five-second samples reject task launches. This check is disabled by default; estimates are not reservations, and concurrent work, model loading, transient peaks, paging and hard limits are not controlled. The gateway currently uses a fixed 24 GiB budget with a 2 GiB reserve; this is unsuitable for adapters with less available memory. Shared-memory counters are warning signals, not proof of allocation origin. `notification-queue.mjs` serializes spoken notifications and defers them when interrupted; behavior under load needs validation.

When enabled, admission is serialized across connections within the gateway process and includes an estimate for each accepted task. Estimates are released after a confirmed terminal result; an ambiguous submission, status error or timeout keeps its estimate held until the gateway exits. This can reject legitimate later work, and the estimates can double-count memory already represented in the sample. Restarting loses the accounting even if an external task remains active; other gateway processes and non-gateway workloads are not coordinated. This does not reserve GPU memory or make a 24 GB limit enforceable.

Admission failures emit `task.rejected` for the client. The cascade path speaks a fixed explanation; the experimental native-speech model may still misdescribe the failure. The isolated real-model check is `scripts/probe-task-rejection.mjs` with `ASSISTAI_TEST_VOICE_URL` targeting a test gateway configured with a missing sample.

## Experimental LFM realtime gateway

Set `ASSISTAI_LFM_REALTIME_URL` to a loopback `/v1/realtime` WebSocket endpoint to opt into the LFM bridge; without it, the existing cascade remains the default. `ASSISTAI_LFM_WORKSPACE_CONTEXT` can provide a short explicit workspace description. This is an experimental developer path, not an automatic model launcher or enforced memory policy. The browser has not yet been tested live in this mode; text and image input are unavailable, and a spoken completion notification passed a synthetic real-model test, but has not been verified in a live browser. OpenCode retains its own permissions and is not an OS sandbox. See [EXP-054](../docs/research/2026-11-10-native-duplex.md#exp-054-opt-in-lfm-gateway-and-synthetic-interruption) for conditions and limits.

An interruption during native tool submission now replaces the voice session and ignores the old tool response; a bounded amount of subsequent audio can wait while the replacement connects. This does not cancel an independently submitted background task. The race has mock coverage but has not been tested with the live native model.

The gateway sends a `session.capabilities` event when the client connects. Native speech mode disables the text and image controls. Set `ASSISTAI_LFM_TRANSCRIPT_ASR_URL=ws://127.0.0.1:18082/asr` to opt into parallel CPU Vosk transcription; otherwise native input transcription is unavailable. It is a separate, potentially inaccurate recognition of the captured audio, not the model's internal interpretation. Final transcripts and assistant responses are saved to local session events. On an upstream reset, a bounded selection of recent events and task results is sent as explicitly untrusted context to the replacement session. This is not cross-connection memory or a prompt-injection boundary. Its connection and buffering are bounded and failures do not stop native speech. The synthetic real-Vosk adapter test is `node scripts/probe-native-transcript.mjs <16kHz-mono-PCM16-file>`. Native browser and real microphone behavior remain unverified.

For both cascade and native modes, the gateway adds bounded recent session events to a newly delegated OpenCode task as untrusted background. A mock gateway test confirms that an earlier result is included in a later task prompt. In one synthetic test, the real local agent returned a random code found only in an earlier session message; the voice controller was mocked. This does not establish general recall or prevent prompt injection.

Session resume is experimental and disabled by default. Start a gateway with `ASSISTAI_ENABLE_SESSION_RESUME=1`, then choose **Start a resumable conversation** in its browser client. This creates a new session and reloads the page; it does not migrate the conversation already open. The browser stores a random bearer key in local storage and sends it in the WebSocket subprotocol; the gateway uses a hash of the key to scope event history and allows only one active connection for that key. The gateway's configured SQLite storage controls retention: `:memory:` survives reconnects only until the gateway exits, while a file can survive restarts. Stopping resume removes the browser key but does not erase SQLite history, and losing the key loses access to that resumed session through this interface.

On reconnect, the browser displays up to 20 recent recorded task events, including results that arrived while it was offline. A mock harness test covers a task actually completing through the gateway while disconnected. These events are labeled as previous events and do not trigger spoken notifications; a recorded start does not establish the task's current state. This is a bounded history snapshot, not an acknowledged notification queue, and the same entries can reappear on reload.

Mock-service tests cover same-key reconnection, separation from a different key, a duplicate active connection, file-backed gateway restart, native-session context delivery and native completed-result reuse after reconnect. Another mock test covers retaining an in-flight task across a same-process reconnect and delivering its completion to the new connection. In one synthetic text test, the real cascade controller recalled a random code after same-key reconnect and did not repeat it in a different session. The UI behavior was tested with a simulated DOM; live browser, real-microphone recall and native-model recall remain unverified. A session key is a bearer capability, not authentication, encryption, RBAC or a substitute for OS isolation. Browser-local scripts with access to local storage, local processes, and readers of the unencrypted database remain relevant to the threat model. Running-task tracking does not survive gateway restart, events occurring while disconnected are not replayed and notification queues are not restored; resuming does not prevent duplicate actions.

Synthetic spoken-input testing recovered one colour after reconnect, while secret-word examples failed and one initial substring-based check was corrected because it counted a denial as success. Real microphone, general spoken recall and native speech-model recall remain unverified. See EXP-109 in the native duplex research notes.

When parallel transcription is configured, the gateway's service list reports its engine, model and health as `Parallel transcription`, distinct from the speech-to-speech model. It is omitted when not configured. Service health is a snapshot and does not establish which model actually produced a particular transcript.

The Windows native client's connection to the native gateway protocol can be exercised without physical audio devices using `node scripts/probe-native-client-mock-gateway.mjs` while the local Vosk sidecar is running. Set `ASSISTAI_TEST_MANUAL_INTERRUPT=1` for a separate simulated manual-interruption and late-audio test. It uses a mock realtime inference server, synthetic input and generated test PCM, and volatile gateway history; it does not demonstrate real-model speech quality or native inference. The client prints the gateway-reported mode on connection.

Native completion notifications pass a bounded excerpt of the completed task result to the speech model, with tools disabled for that response. The full result appears in the client. The generated summary is not guaranteed accurate and untrusted result text is not isolated from the model.

Cascade completion notifications now send an explicitly labeled, normalized excerpt of up to 300 Unicode characters from the same-session result directly to local TTS. This is not a model-generated summary; longer results are truncated and the full text remains displayed. Mock-service tests verify the TTS request and reject a different session's task ID. Audible accuracy is unverified, and result excerpts may contain sensitive data.

The guarded coding probe supports `-Notification` with synthetic text or spoken input. One real-agent text run completed the fixture and produced notification audio using the existing local Pocket TTS; the recording was not heard or independently transcribed. The combined spoken-input and notification path has mock event-sequencing coverage but has not completed a real-model run; its initial preflight found insufficient available RAM. Neither test uses a live microphone. See EXP-132 and EXP-136.

A subsequent guarded combined trial passed preflight but the synthetic speech transcript distorted the filename and omitted the distinction between operations; the controller then delegated the opposite change. The RAM watchdog stopped the trial before completion, and the fixture remained unchanged. The current spoken coding path is not dependable. See EXP-144.

The updated cascade offers optional **Review speech before sending**. After speech ends, the transcript appears in the text field; edit it and press Send. A selected spoken image remains bound to that reviewed turn, and capture pauses while review is pending. Disabling review discards the pending server-side turn; disconnecting also loses it. The option is disabled in native speech mode and older gateways. Mock tests cover editing and image binding, but real microphone use and general task correctness remain unverified. See EXP-154.

`scripts/run-asr-coding-probe.ps1` is a guarded synthetic recognition probe for three fixed French examples involving operation direction, negation and a filename. Token order and word error are not semantic correctness or a substitute for real microphone tests. See EXP-145 and EXP-155.

One three-phrase run completed; both recognizers missed the filename. See EXP-153 and EXP-155.

`python scripts/setup-crispasr-cpu.py` obtains a pinned SHA-256-verified Windows CPU research binary in a new cache directory and refuses to overwrite an existing destination. On this machine it starts and lists `fastconformer-ctc` and `kyutai-stt`; an existing French Q8 FastConformer GGUF is 117,361,632 bytes. Neither backend advertises native streaming in this binary's capability list. The FastConformer model has been used in one small synthetic file comparison, but is not part of the demo. See EXP-152 and EXP-155.

`python scripts/setup-transcribe-runtime.py` prepares a separate pinned Windows CPU/Vulkan transcribe.cpp research library; `python scripts/probe-transcribe-runtime.py` checks its contract and initializes CPU discovery only. The installed release contains a DLL rather than a CLI. An existing 2,830,493,984-byte Voxtral Realtime Q4 GGUF is a candidate, but it has not been loaded, benchmarked or integrated, and B60 Vulkan behavior is unknown. The probe's CPU selection does not prove Vulkan availability. See EXP-156.

The same CPU-only probe verifies selected native structure sizes and alignments before calling their initializers. The versioned API documents AUTO, FP16 and FP32 for its encoder attention KV field and says the generic context cap is ignored by Voxtral Realtime. Family-specific cache behavior, actual memory and support for quantized KV remain unverified; see EXP-157.

`python scripts/inspect-voxtral-cache.py <model.gguf>` reads selected metadata without loading weights and estimates K/V tensor sizes for the pinned streaming implementation. The local checkpoint gives 768 MiB FP32 encoder plus 832 MiB FP16 decoder KV, excluding all other allocations. The pinned path does not implement quantized KV for these rings, and no actual allocation or latency has been measured. See EXP-158.

After the spoken-coding trial, the running agent model retained host memory even when its slot was idle. Its `action=erase` request returned HTTP 501 because slot actions were not enabled at server startup; no cache was erased. This did not recover enough headroom for the benchmark. Changing startup flags or restarting the model has not been tested as a recovery method in this configuration. See EXP-150.

The updated gateway advertises task cancellation when OpenCode is configured. The browser's **Stop latest agent task** button requests cancellation for an active same-session task. An accepted request does not confirm completion, undo changes or release the task's resource estimate; the existing poll handles terminal status. Reconnected historical tasks and tasks with failed or uncertain polling may not be cancellable from the button. Older gateways leave it disabled. This has mock coverage only, not a live harness test; see EXP-146.

The client tracks multiple tasks started during the current connection. If the newest finishes or already has an outstanding cancellation request, the button targets the most recent remaining task; a rejected request can be retried. Historical tasks after reconnect are not reconstructed as active, and the button does not provide a task picker. See EXP-147.

When submission or polling is uncertain, the updated gateway keeps the task ID and admission estimate, emits `task.uncertain`, retains same-session cancellation and rejects an identical normalized submission instead of creating another task. Status polling retries up to three consecutive failures; after exhaustion, or an ambiguous submission, the task stays uncertain without automatic reconciliation. Different wording may create another request, and gateway restart loses the task map. Mock tests cover recovery from one polling failure, cancellation and estimate release on observed completion; ambiguous submission and real OpenCode behavior need further verification. See EXP-148 and EXP-149.

The browser retries busy notification requests up to three times and logs a failure if they cannot be spoken; the written result remains visible. The retry behavior is covered by client mocks and requires a restarted gateway for explicit rejection reasons. Older gateways send an unclassified rejection, which is reported without retry. Live browser behavior is not yet verified.

`scripts/run-notification-transcription.ps1` separately tests a synthetic result notification through local Pocket TTS and Vosk under sampled Windows B60 memory guards. Of three short examples, the independent ASR recognized the expected marker twice; one initial recognition failed and its repeat passed. Audio remains in memory and no physical devices are opened. This is a small loopback-content check, not a substitute for listening or a general quality benchmark. See EXP-133.

After a native reset or opt-in reconnect, an exact normalized completed task can be reused unless the model sets the `rerun` tool flag. Reconnect reconstruction uses matching start and completion records among at most 400 recent task events and retains at most 100 results. This prevented the observed duplicate in one real-model synthetic reset test; reconnect reuse was tested with mocks only. Different wording, a model-selected rerun, in-flight work, incomplete history or cache eviction can still repeat actions; reuse can also return stale results. The model's decision to set `rerun` is not independently verified against the user's speech. The regression probe is `scripts/probe-lfm-reset-context.mjs` and requires synthetic fixture files and the isolated native trial described in the research notebook.
